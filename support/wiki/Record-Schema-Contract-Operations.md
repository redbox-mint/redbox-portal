# Operating Record Schema Contracts

ReDBox can compile the authoritative form selected for a create or update into
an immutable JSON Schema artifact, validate the submitted metadata against that
artifact, and retain the artifact while a grant, successful save, or configured
integration pin refers to it. This page is the operator runbook for enabling,
observing, enforcing, retaining, and troubleshooting that feature.

The feature is **disabled by default**. Its default unknown-property policy is
**`allow`**, preserving metadata properties that the form contract does not
declare. Enabling schema generation does not itself enable rejection: the
existing [`recordValidation`](Server-Side-Form-Validation-Operations) rollout
policy supplies the effective `shadow` or `enforce` mode for each record type
and validation operation.

## Configuration

The complete core default is:

```javascript
recordSchema: {
  enabled: false,
  unknownProperties: 'allow',
  contractFormat: 'redbox-record-contract/1',
  cacheMaxEntries: 128,
  limits: {
    maxDepth: 64,
    maxProperties: 10000,
    maxDocumentBytes: 1048576,
    maxDiagnostics: 1000,
    contributorTimeoutMs: 1000
  },
  retention: {
    minimumAgeDays: 365
  }
}
```

Override `recordSchema` through the normal Sails configuration layers described
in the [Configuration Guide](Configuration-Guide). All numeric values must be
positive integers. Environment-backed string values `"true"` and `"false"` are
normalized for `recordSchema.enabled`; do not rely on string coercion for other
values.

| Key | Default | Meaning |
|---|---:|---|
| `recordSchema.enabled` | `false` | Activates startup checks, schema resolution, structural write validation, artifact/grant persistence, save references, and retention operations |
| `recordSchema.unknownProperties` | `allow` | Global object-boundary policy: `allow` preserves undeclared properties; `declared` reports them as `record-schema.additional-property` |
| `recordSchema.contractFormat` | `redbox-record-contract/1` | Compiler and annotation format; v1 is the only supported value |
| `recordSchema.cacheMaxEntries` | `128` | Maximum process-local compiled-validator cache entries |
| `recordSchema.limits.maxDepth` | `64` | Maximum contract/contributor nesting depth |
| `recordSchema.limits.maxProperties` | `10000` | Maximum properties accumulated by one contract |
| `recordSchema.limits.maxDocumentBytes` | `1048576` | Maximum UTF-8 byte length of the canonical schema document |
| `recordSchema.limits.maxDiagnostics` | `1000` | Maximum compiler diagnostics and structural validation issues retained for a result |
| `recordSchema.limits.contributorTimeoutMs` | `1000` | Wall-clock timeout for contributor work |
| `recordSchema.retention.minimumAgeDays` | `365` | Minimum whole-day artifact age before a report can mark it deletion-eligible |
| `recordSchema.integrationPins` | omitted | Optional array of at most 100 durable integration references; see [Retention pins](#retention-pins) |

A record type may override only the unknown-property policy:

```javascript
// Within one config/recordtype.js definition
recordSchema: {
  unknownProperties: 'declared'
}
```

The record-type value takes precedence over
`recordSchema.unknownProperties`. Clients cannot select this policy. Use
`declared` only after shadow traffic has shown that legacy and integration-owned
properties are represented by the effective forms. The policy applies at every
object boundary generated by the contract, not just the metadata root.

## Storage capability

Existing custom storage hooks remain source-compatible while the feature is
disabled because the schema methods are optional in `StorageService`. When
`recordSchema.enabled` is `true`, startup requires the selected storage provider
to implement every method in this capability set:

| Method | Required behavior |
|---|---|
| `putRecordSchemaArtifact` | Idempotently persist canonical immutable content and reject a digest/content collision |
| `getRecordSchemaArtifact` | Read an artifact by lowercase SHA-256 digest |
| `listRecordSchemaArtifacts` | Return bounded digest/creation-time summaries in stable digest order for retention pages |
| `touchRecordSchemaArtifact` | Update access metadata without changing artifact identity |
| `putRecordSchemaReference` | Idempotently persist a validated `grant`, `save`, or `pin` reference and reject reference-key collisions |
| `listRecordSchemaGrants` | Return bounded grants used to authorize immutable retrieval |
| `listRecordSchemaReferences` | Return bounded reference evidence for usage and retention |
| `deleteRecordSchemaArtifactIfUnreferenced` | Atomically recheck age and live references before deleting an eligible artifact |

The bundled Mongo storage hook implements this set with the
`recordschemaartifact` and `recordschemareference` models. Artifacts have a
unique `digest` index. References have a unique `referenceKey` index plus
indexes for digest/kind, OID/kind, and pin expiry. Artifact writes are
content-addressed and immutable; a second write is successful only when its
content identity matches. Reference writes must not create a reference to an
unknown artifact.

The delete method is part of the capability so any future maintenance caller
cannot use an unsafe read-then-delete adapter. The first delivery does not
schedule deletion or expose a destructive maintenance operation; its service
surface produces a report/dry run only.

## Rollout and auditing shadow output

Start with the feature enabled and validation left in its default `shadow`
mode:

```javascript
recordSchema: {
  // Include the other core defaults when your config layer replaces objects.
  enabled: true,
  unknownProperties: 'allow',
  contractFormat: 'redbox-record-contract/1',
  cacheMaxEntries: 128,
  limits: {
    maxDepth: 64,
    maxProperties: 10000,
    maxDocumentBytes: 1048576,
    maxDiagnostics: 1000,
    contributorTimeoutMs: 1000
  },
  retention: { minimumAgeDays: 365 }
},
recordValidation: {
  mode: 'shadow',
  timeoutMs: 5000,
  shadowReportMaxSeries: 1000
}
```

Schema failures governed by rollout policy become safe save warnings in shadow
mode. A committed invalid candidate is returned as `saved-with-warnings`; its
problems have `source: 'schema'`, `phase: 'schema'`, stable codes, RFC 6901
pointers, and allowlisted expected-type details. When schema resolution
succeeds, the non-persisted `schemaOutcome` reports the digest, immutable URL,
`complete` or `partial` completeness, and effective enforcement mode. Do not
copy `schemaOutcome` into record metadata.

Shadow is not an authorization or concurrency bypass. An unknown or
unauthorized validation operation, denied record access, missing authoritative
update record, malformed schema precondition, or mismatched schema
precondition still rejects the request in every mode.

Before enforcing any operation:

1. Run `npm run test:record-contracts` and resolve all coverage, deterministic
   output, meta-schema, and configured-limit failures.
2. Lift one representative environment with `recordSchema.enabled: true` and
   global `recordValidation.mode: 'shadow'`. Confirm the startup lifecycle and
   integration-pin checks pass.
3. Exercise representative create, partial update, and workflow-transition
   writes for every named operation. Audit omitted-operation traffic separately
   because it resolves to the `strict-all` contract.
4. Aggregate `saved-with-warnings` schema problems by record type, operation,
   form, schema kind, digest/completeness, and code outside the process. Review
   `redbox.record_schema.validation.*`, resolver, completeness, limit,
   persistence, and usage-reference telemetry at the same time.
5. Use `RecordValidationService.getShadowReport()` and
   `record_validation_completed` telemetry alongside this evidence for the
   form/business-validator phase. That process-local report does **not** replace
   collection of structural schema warnings from save outcomes.
6. Classify and remediate unsupported or partial components, legacy
   nullability, undeclared properties, historical invalid values, timeouts,
   configuration failures, storage failures, and diagnostic truncation. Keep
   `overflowRuns` at zero in the validation report and retain deployment-level
   evidence from exported telemetry.
7. Obtain signoff for one `(record type, operation)` unit, then set only that
   unit to `enforce`. Monitor rejection, unavailable, partial, limit, and
   post-save reference-warning rates before expanding.

Enforcement precedence remains:

```text
recordValidation.mode
  -> recordValidation.operations[operation].mode
  -> recordtype.<type>.recordValidation.mode
  -> recordtype.<type>.recordValidation.operations[operation].mode
```

For example, leave the deployment and record type in shadow while enabling one
reviewed operation:

```javascript
// Within one config/recordtype.js definition
recordValidation: {
  mode: 'shadow',
  operations: {
    publish: { mode: 'enforce' }
  }
}
```

Rollback the smallest affected operation to `shadow`; this keeps evidence
flowing. Setting `recordSchema.enabled` back to `false` is a feature rollback
that also stops schema resolution, validation, persistence, and telemetry, so
it is less useful while diagnosing a contract mismatch.

## Limits and bounded work

The configurable compiler, document, diagnostic, timeout, and cache limits are
listed above. The service also has fixed defensive bounds:

| Work | Bound |
|---|---:|
| Configured integration pins | 100 |
| Configured forms inspected at startup | 1000 |
| Startup findings exposed in structured logs | `finding_count` is capped at 100; larger totals also use `finding_count_bucket: 'overflow'`. The thrown `RecordSchemaLifecycleError.findings` retains the full findings. |
| Immutable-grant lookup | 1000 rows per page, at most 10 pages |
| Targeted retention report | 100 input digest entries before deduplication |
| Paginated retention report | 100 artifacts per page; default 100 |
| References examined for one retention digest | 1000, followed by a one-row overflow probe |
| Storage reference query | 1000 rows |

Exceeding a configured compiler/document bound produces the corresponding
`record-schema.limit-*` code. Exceeding a maintenance/report bound produces
`record-schema.limit-exceeded`; the operation fails closed instead of returning
an incomplete answer. `record-schema.limit-diagnostics` in a save result means
the issue list was truncated and is not sufficient enforcement evidence.

## Retention pins

Use a pin when an external integration must keep an exact immutable digest even
without a current grant or recorded save:

```javascript
recordSchema: {
  // ...the normal keys...
  integrationPins: [
    {
      digest: '0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef',
      brand: 'default',
      portal: 'rdmp',
      schemaKind: 'update',
      recordType: 'rdmp',
      operation: 'publish',
      owner: 'repository-integration-team',
      purpose: 'Retain the schema used by the repository deposit mapping.',
      expiresAt: '2027-08-27T00:00:00.000Z'
    }
  ]
}
```

Each pin requires `digest`, `brand`, `portal`, `schemaKind`, `recordType`,
`operation`, `owner`, and `purpose`. The digest is lowercase 64-character
SHA-256 hex; `schemaKind` is `create` or `update`; and `operation` follows the
validation-operation name grammar and is trimmed before persistence. Digest,
brand, portal, record type, owner, and purpose must be trimmed and non-empty.
Brand, portal, record type, and owner are limited to 512 characters; purpose is
limited to 2048. `expiresAt`, when present, must have a valid calendar date and
use `YYYY-MM-DDTHH:mm:ssZ` or `YYYY-MM-DDTHH:mm:ss.sssZ`; either form may use a
numeric `+HH:mm` or `-HH:mm` offset instead of `Z`. Hours are `00`–`23`, minutes
and seconds are `00`–`59`, and fractional seconds are either absent or exactly
three digits. Whitespace and leap seconds are not accepted. Omit `expiresAt`
only for an intentionally permanent pin.

Pins are deterministically keyed, deduplicated, sorted, and idempotently
materialized after all lifecycle checks and configured-form compilation pass.
Application readiness waits for every configured pin write. The artifact must
already exist; an unknown digest produces `record-schema.artifact-not-found`
and blocks startup.

Pin materialization is additive. Removing a pin from configuration does not
delete an already persisted reference, and this delivery has no reference
deletion surface. Prefer an explicit reviewed expiry unless permanence is a
hard integration requirement. A pin is active only while it has no expiry or
its expiry is later than the report's `now`; expired pins are ignored as
retention reasons.

## Retention report and dry run

`RecordSchemaService.reportRetention()` is an internal, non-destructive service
operation. It has no public route and never calls
`deleteRecordSchemaArtifactIfUnreferenced`.

Use a stable operator-supplied `now` so repeated runs are comparable. Scan
storage-owned pages:

```typescript
await RecordSchemaService.reportRetention({
  mode: 'paginated',
  now: new Date('2026-08-27T00:00:00.000Z'),
  limit: 100,
  // cursor: previousResult.page.nextCursor
});
```

Or inspect a known set of at most 100 digests:

```typescript
await RecordSchemaService.reportRetention({
  mode: 'targeted',
  now: new Date('2026-08-27T00:00:00.000Z'),
  digests: ['0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef']
});
```

Successful output is deterministic and contains `now`, `minimumAgeDays`,
`entries`, `missingDigests`, and paginated mode's `page.limit` and optional
`page.nextCursor`. Each entry contains only digest, creation time, whole-day
age, grant/save/active-pin counts, ordered reasons, and
`eligibleForDeletion`. It does not include a schema document, OID, pin owner,
or pin purpose.

The retention reasons are:

- `minimum-age`: artifact age is less than
  `recordSchema.retention.minimumAgeDays`;
- `grant-reference`: at least one live retrieval grant exists;
- `save-reference`: at least one successful-save usage reference exists;
- `active-pin`: at least one unexpired configured pin exists.

`eligibleForDeletion: true` means that no reason was observed in this bounded
dry run. It is not a deletion authorization or evidence that deletion occurred.
Any future deletion caller must still use the storage capability's atomic final
age/reference recheck.

## Startup failures and diagnostics

When disabled, `RecordSchemaService` reports the lifecycle as `disabled` and
does not inspect storage or contributors. When enabled, the complete gate runs
after the configured storage provider is ready and before Sails reports
application readiness. It aggregates deterministic findings, compiles every
configured form, then materializes pins.

An aggregated gate failure is a `RecordSchemaLifecycleError` with top-level
code `record-schema.lifecycle-failed` and sorted `findings`:

| Category | Primary code | Diagnostic fields and action |
|---|---|---|
| `configuration` | `record-schema.config-invalid` | `path` and `reason`; restore every required key and a supported, correctly typed value |
| `storage` | `record-schema.storage-unavailable` | `method`; install/enable the complete eight-method capability |
| `contributor` | `record-schema.contributor-invalid` or `record-schema.contributor-duplicate` | `registrationCode` and safe contributor `key`; fix hook discovery/registration |
| `coverage` | `record-schema.unsupported-component` | `componentType`; a persisted core component has no contributor |
| `form` | Compiler, contributor, contract, or limit code | `form` and `stage` (`candidate`, `compiler`, `renderer`, or `artifact`); fix the effective configured form or contributor |
| `pin` | `record-schema.config-invalid` | Pin `path` and reason such as `digest`, `operation`, `datetime`, or `maximum-length` |

After that gate passes, a pin persistence failure also blocks readiness. Its
error states that configured pins were not materialized and includes the sorted
stable failure codes, commonly `record-schema.artifact-not-found`,
`record-schema.reference-key-collision`, or
`record-schema.storage-unavailable`.

Contributor findings carry one of these exact registration codes:

- `record-contract.registration.invalid-key`
- `record-contract.registration.invalid-version`
- `record-contract.registration.invalid-component-type`
- `record-contract.registration.invalid-namespace`
- `record-contract.registration.invalid-pointer`
- `record-contract.registration.duplicate-key`
- `record-contract.registration.duplicate-component`
- `record-contract.registration.duplicate-namespace`
- `record-contract.registration.overlapping-root`
- `record-contract.registration.form-path-overwrite`
- `record-contract.registration.invalid-export`

The privacy-safe structured startup event is `record_schema_startup_check`.
Its context is `lifecycle`, `startup-configured-forms`, or `integration-pins`;
status is `disabled`, `passed`, or `failed`. Unexpected caught failures use
`record_schema_unexpected_failure` with a bounded context and `error_type` of
`error` or `non-error`, never raw exception text or record/form values.

## Stable record-schema codes

These are the complete stable codes emitted by the record-schema service and
write boundary.

| Code | Meaning |
|---|---|
| `record-schema.config-invalid` | Global, record-type, or pin configuration is missing, malformed, or unsupported |
| `record-schema.authentication-required` | Schema resolution requires an authenticated caller |
| `record-schema.invalid-request` | Request, digest, operation, conditional header, validation input, or maintenance input is malformed |
| `record-schema.not-found` | The requested record or accessible immutable schema was not found |
| `record-schema.forbidden` | The caller is authenticated but not authorized for the requested schema context |
| `record-schema.not-resolvable` | No authoritative effective form/schema context can be resolved |
| `record-schema.limit-exceeded` | A bounded resolver, lookup, startup, pin, or report operation exceeded its safe cap |
| `record-schema.invalid-contract` | Generated, persisted, or supplied schema/reference state fails contract or meta-schema checks |
| `record-schema.unavailable` | The feature or required resolution/service dependency is unavailable |
| `record-schema.storage-unavailable` | The storage provider, method, read, touch, or reference operation is unavailable |
| `record-schema.artifact-write-failed` | Immutable artifact persistence failed |
| `record-schema.grant-write-failed` | Grant persistence failed after artifact handling |
| `record-schema.digest-collision` | Existing content under a digest does not match the attempted immutable content |
| `record-schema.reference-invalid` | A grant, save, or pin reference violates its storage contract |
| `record-schema.reference-key-collision` | Existing content under a deterministic reference key does not match |
| `record-schema.artifact-not-found` | A reference targets an artifact that is not stored |
| `record-schema.limit-depth` | Contract or contributor output exceeded `limits.maxDepth` |
| `record-schema.limit-properties` | Contract exceeded `limits.maxProperties` |
| `record-schema.limit-document-bytes` | Canonical schema exceeded `limits.maxDocumentBytes` |
| `record-schema.limit-diagnostics` | Diagnostics/issues reached `limits.maxDiagnostics` and output was truncated |
| `record-schema.limit-contributor-timeout` | Contributor work exceeded `limits.contributorTimeoutMs` |
| `record-schema.contributor-invalid` | Contributor registration or output is invalid |
| `record-schema.contributor-duplicate` | Contributor identity, component type, or namespace conflicts |
| `record-schema.contributor-failed` | Contributor execution failed |
| `record-schema.unsupported-component` | No contributor can represent a component; core coverage is startup-fatal, while a custom component can make a runtime contract partial |
| `record-schema.precondition-failed` | A supplied update-schema ETag does not match the authoritative digest |
| `record-schema.type` | Submitted value has the wrong JSON type |
| `record-schema.additional-property` | `declared` policy rejected an undeclared object property |
| `record-schema.required` | A required property is missing |
| `record-schema.enum` | A value is outside the allowed enumeration |
| `record-schema.array-item` | An array item failed its item contract |
| `record-schema.validation` | Safe generic fallback for a structural keyword/problem without a more specific mapping |

`record-schema-save-usage-failed` is the post-commit save warning when the
record was confirmed persisted but its durable schema usage reference was not.
The safe structured event is
`record_schema_save_usage_persistence_failed`; reconcile the reference before
treating retention evidence as complete.

The route-schema labels `record-schema-digest-invalid`,
`record-schema-if-none-match-invalid`, and `record-schema-if-match-invalid` are
internal request-parser diagnostics. They map to the stable
`record-schema.invalid-request` problem/save code; operators should alert on
the stable code rather than those parser labels.

## Telemetry and privacy

The OpenTelemetry meter is `redbox.record-schema` and emits:

| Instrument | Type | Attributes | Purpose |
|---|---|---|---|
| `redbox.record_schema.compile.duration` | histogram, ms | `schema_kind`, `phase`, `outcome` | Resolution, startup, and validation compilation latency |
| `redbox.record_schema.compile.outcomes` | counter | `schema_kind`, `phase`, `outcome` | Compilation outcome volume |
| `redbox.record_schema.cache.results` | counter | `schema_kind`, `result` | Compiled-validator cache hit/miss volume |
| `redbox.record_schema.completeness` | counter | `schema_kind`, `completeness` | Complete versus partial resolved schemas |
| `redbox.record_schema.resolver.outcomes` | counter | `schema_kind`, `outcome` | Create/update/immutable resolution outcomes |
| `redbox.record_schema.validation.results` | counter | `schema_kind`, `result` | Valid, invalid, invalid-input, and unavailable structural validation results |
| `redbox.record_schema.validation.problems` | counter | `schema_kind`, `code` | Invalid structural results by stable allowlisted code |
| `redbox.record_schema.precondition.mismatches` | counter | `schema_kind`, `condition` | Update `if-match` schema mismatches |
| `redbox.record_schema.persistence` | counter | `resource`, `outcome`, `code` | Artifact and grant persistence results |
| `redbox.record_schema.usage_references` | counter | `reference_kind`, `outcome`, `code` | Save-reference and integration-pin materialization results |

`schema_kind` is bounded to `create`, `update`, or `unknown`. Outcomes and codes
are reduced to fixed allowlists, and no record OID, request ID, actor, role,
form value, schema document, field pointer, pin owner/purpose, or raw exception
text is used as a metric attribute. Configure the deployment's OpenTelemetry
SDK/exporter to retain these instruments; they are process telemetry, not a
durable schema audit store.

## Troubleshooting

### The portal does not become ready after enabling the feature

Find the `RecordSchemaLifecycleError` and read every sorted finding, not only
the first. Fix categories in order: configuration, missing storage methods,
contributor registration, core coverage, configured forms, then pins. Confirm
the final `record_schema_startup_check` lifecycle and integration-pin events are
both `passed`.

### Startup fails only while materializing pins

Confirm the exact digest already exists, the pin is trimmed and within field
limits, and the deterministic key is not bound to different content. Treat
`record-schema.reference-key-collision` as conflicting durable state, not a
retryable outage. Storage unavailability is retryable only after storage health
has been restored.

### Shadow writes return many `record-schema.additional-property` warnings

Confirm whether the effective global or record-type policy is `declared`.
Inventory the pointers by `(record type, operation, form)` and add legitimate
fields to the authoritative form/contributor contract before enforcement. Use
`allow` during compatibility rollout; do not strip submitted properties as a
workaround.

### Schemas are unexpectedly partial

Check `redbox.record_schema.completeness`, response `schemaOutcome`, and compiler
diagnostics for `record-schema.unsupported-component`, legacy nullability, or an
unrepresentable condition. Missing coverage for a persisted core component is
startup-fatal; hook/custom components may deliberately produce a partial
contract and require deployment-specific signoff.

### Saves succeed but retention reports show no save reference

Look for `record-schema-save-usage-failed`, the
`record_schema_save_usage_persistence_failed` event, and
`redbox.record_schema.usage_references{reference_kind="save"}` failures. The
record commit is not rolled back by this post-commit failure. Repair storage,
then reconcile the durable reference before relying on deletion eligibility.

### A retention report stops with a limit or invalid-state result

Do not treat a partial scan as evidence for deletion. A per-digest reference
overflow returns `record-schema.limit-exceeded`; malformed persisted artifact or
reference summaries return `record-schema.invalid-contract`; read failures
return `record-schema.storage-unavailable`. Repair or investigate the durable
state and rerun the same bounded page with the same `now`.
