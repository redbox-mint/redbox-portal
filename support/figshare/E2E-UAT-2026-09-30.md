# Queued Figshare UAT end-to-end check — 2026-09-30

The local `cqu-figshare-queued` stack was connected to CQU Figshare UAT. The test created ReDBox dataset `c8b0ed23040d4b52b88cbea7cd12365b`, titled `Queued Figshare E2E UAT 2026-09-30T00:08:57.347Z`, and Figshare article `11543456`. The article remains in the authenticated account at <https://cqu.figsh.com/account/articles/11543456>. No Figshare data was deleted or made public.

The ReDBox API created the local record because the local database has no party records for the contributor lookup required by the dataset form. The API fixture initially omitted a licence; the queued transition rejected it locally. Adding CC BY 4.0 allowed the transition. The first worker attempt then stopped because the configured local service username did not exist; the local AppConfig was changed to the existing `admin` user. The worker created one Figshare article and wrote its ID and URL back to the ReDBox record.

Figshare rejected the first publish request with HTTP 400, `Missing mandatory value: Central Queensland University ROR`. The form's default ROR had not been supplied by the API fixture. After adding `https://ror.org/023q4bk22` and the contributor name, a corrected source save reused article `11543456`, updated its metadata and had its publish request accepted. The authenticated Figshare page shows the ROR, title, description, keyword, contributor and CC BY 4.0 licence. It labels the article `Private version`. The local sync state is `waiting`, `publication=pending`, `publish.outcome=accepted`, `waitingReason=review`, with no active lease or error. Manual curation is the expected endpoint; public publication was not exercised.

The HTTP 400 exposed a recovery defect: a definite validation rejection was checkpointed as an uncertain publish result, so a corrected source save could wait indefinitely for publication confirmation. The worker now marks only the specific HTTP 400 `BadRequest` / `Missing mandatory value:` response as rejected and retries after a newer source generation only when the same article is still unpublished and has not advanced beyond the recorded version. A controlled test verifies that the retry reuses one article. The HTTP failure logger now records bounded validation details without Axios request internals; its test checks that neither the Authorization header nor token appears in those details.

The existing UAT checkpoint predated the fix. After confirming through a read-only Figshare request that this article remained unpublished at the recorded version, the local test sync checkpoint was changed from `uncertain` to `rejected`, then the corrected source save was processed. That manual local repair was only for this test record.

Limits and follow-up: the API-created record did not prove a complete form-driven submission; its edit form currently reports required FoR Codes. The local Figshare category crosswalk IDs are blank, so no categories were sent. The local service username must refer to a real user. The CQU manual curation step and any eventual public publication were outside this test and must not be inferred from the accepted publish request. The configured UAT token remains in the local AppConfig and is not recorded here.
