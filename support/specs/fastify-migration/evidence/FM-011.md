## Implementation

[`FastifyHost.ts`](../../../../packages/redbox-core/src/http/fastify/FastifyHost.ts)
owns one supplied application runtime and one Fastify instance/underlying
`node:http.Server`. Construction installs neither a listener nor process signal
handlers. The prepare callback receives that same server for borrowed integration
attachment and registers the complete route/plugin graph after application
initialization. It must not listen or close shared application dependencies.

`initialize()` joins concurrent calls and awaits application initialization,
preparation, **`fastify.ready()`**, then listen. `activate()` is separate and joins
concurrent calls. The host opens admission only after application activation
succeeds; readiness also requires the application's current readiness. The host
uses FM-010's `createPortalRouter`, preserving its router configuration/raw URL
restoration. Route composition owns any root-context prefix; probes stay global.

A root `onRequest` hook runs before prepared plugin hooks, body parsing, actions
and fallback. While inactive, activating, failed or stopping, ordinary traffic
gets **503**, `{"error":"application-not-ready"}`. The host's safe miss is **404**,
`{"error":"not-found"}`. No automatic validators or powered-by header are added.

Probe behavior follows [FM-003](FM-003.md): only exact global **GET** `/healthz`
and `/readyz`, optionally with a query string, are intercepted. Health returns
**200**, `{"healthy":true}` while live, independently of readiness, and **503**,
`{"healthy":false}` after a host failure/failed stop. Readiness returns **200**,
`{"ready":true}` only after activation, otherwise **503**, `{"ready":false}`.
There are no synthetic probe HEAD handlers or case/slash/root-prefixed probe
aliases. JSON responses retain `application/json; charset=utf-8`, byte length,
absent ETag/powered-by/cache/Allow headers and bodyless HEAD behavior.

Failures in initialization, preparation, plugin boot, readiness, listen or
activation close admission and enter host-owned cleanup, preserving the original
startup error. `status()` retains ExpressHost's fields (`ready`, `listening`,
`prepared`, `stopped`, `stopFailed`, `failure`, `application`); preparation/boot/
listen failures use its existing `initialize` failure phase.

Stop closes admission and quiesces the application synchronously, joins concurrent
callers, and waits for the raw in-flight startup stage before transport/application
cleanup. It stores one Fastify-close promise, retains failed/expired stop state,
and never restarts a stopped host. Application cleanup remains application-owned.
This is the startup/admission coordination needed here; the broader accepted-work,
session/disconnect, failed transport-close and cleanup ownership/retry proof remains
**FM-012**, as assigned by the specification.

`installSignalHandlers()` is explicit executable opt-in for SIGINT/SIGTERM. Imports
and construction install nothing. One handler pair joins stop; a failed stop
reports through the executable callback and retains handlers for another signal.
Successful stop removes only owned handlers. The host makes no process exit
decision. No new production executable or host selector is introduced.

### Protection and boundary audit

- `requestTargetPath` catches legacy `node:url.parse` failures. `rewriteUrl`
  always returns a string and uses `/` solely to reach guarded request hooks.
  The first root hook restores the original target and emits the fixed Express
  HTML response on parse failure, before admission, extension hooks or actions.
  This does not normalize dot segments or decode probe paths. The synchronous
  core constraint reuses this nonthrowing helper.
- Fastify 5.12.8 `wrapRouting` invokes rewrite and native constraint derivation
  without a catch; these are the relevant pre-routing paths. Its ordinary
  `onRequest` hook runner catches synchronous exceptions and subscribes to async
  hook rejections. The host admission callback is async, so a thrown application
  status operation is handled there. Both hook modes and admission failure are
  injected in the compiled child and recover on a following request.
- Native `frameworkErrors` is called directly outside those hooks. The owned
  handler uses fixed JSON, fixed headers and the raw response after hijacking;
  it neither reflects target/provider errors nor invokes extension serialization
  hooks. Native bad URL / parameter length errors map to **400 / 414**;
  unexpected async-constraint errors map to a bounded **500**. The callback-based
  native async-constraint error path is exercised before and after activation.
  Core percent shielding and the transport limit prevent the native bad-escape /
  excessive-param paths in normal composed routing.
- `clientErrorHandler` emits fixed bodyless **400 / 408 / 413 / 431** responses,
  matching Node's defaults. It writes only to a writable, live socket before a
  response has sent headers, then destroys the socket without supplying another
  error. Node's HTTP `socketOnError` installs its error sink before emitting
  `clientError`; no additional socket error listener is needed. Real malformed
  method/header requests, all four injected socket-error classes, real TCP resets
  and partial-request disconnects verify recovery. Injected errors occur after a
  partial method has been read to avoid an artificial unread-data reset race.
- The host uses Fastify's default server construction: no custom `serverFactory`
  or additional core request listener. The resolved single-address listen path,
  one prepared server, and both IPv4-first/IPv6-first assertions remain covered.
  The bounded `qs` parser does not throw on malformed percent escapes/limit excess;
  existing FM-010 query/routing regressions remain selected. No process-level
  catch-all is installed and no arbitrary extension callback is silently swallowed.
