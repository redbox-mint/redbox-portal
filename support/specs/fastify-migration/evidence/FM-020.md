# FM-020 — Scoped raw upload and progress socket qualification

This record supersedes the first FM-020 qualification, including its fixture-only
wiring. Review corrections were made on `feature/fastify-migration`, based on
`7c15c19c395251b1136d3e6f2691ef6dd88a8b87`. No commit, branch, worktree, dependency
upgrade, production entrypoint switch or task-checkbox change was made.

**Round-2 security correction:** current Express production had the same
existing-`sid` polling-origin bypass as Fastify. Both now reject that traffic.
This is the one deliberate Express behavior change; see the round-2 evidence below.

**Round-3 composition correction:** raw parser, progress transport and metadata
prelude ownership now follow the final resolved routes, including valid deny,
redirect and controller-subclass replacements. See the round-3 evidence below.

## Production composition and review corrections

1. **Production registration (P1).** `resolvePortalInstallation` selects the
   datastream controller factory when the canonical `addDataStreamsRoute` enters
   the explicit conversion scope. The factory retains the RecordController
   identity and inherited metadata actions. Selecting `progress: true` registers
   the existing progress grant declaration and its explicit controller factory.
   Both actions retain the selected production policies and API CSRF guard.
   A `portal-raw-http` module enters the same resolved dependency graph; it borrows
   the selected disks, datastream, records and progress domains. Its lifecycle
   owns multipart staging and Socket.IO. Production host preparation attaches
   the integration to the host's existing server before plugin readiness/listen,
   and installs raw parsing only in the upload's encapsulated route scope.
   Metadata and other JSON/form routes retain their ordinary parsers. Raw upload
   validation stays in its shared action, after policies/CSRF, rather than
   rejecting the deliberately unread body in generic controller validation.
2. **Wrapper cleanup (P2).** Borrowed Socket.IO dispatch keeps an explicit
   forwarding node. Cleanup retires that node and restores predecessors only
   while the node is directly installed. A later integration may still reach
   retired forwarding nodes without separately registered duplicate dispatchers.
   Real stacked Socket.IO attachments are exercised in both close orders; one
   ordinary GET reaches the original dispatcher exactly once throughout cleanup.
3. **Native session credentials (P2).** Production wiring binds grants to the
   existing FM-014 Mongo session owner, not a second store/client. The store's
   accepted-work lookup uses the same namespace, document version and authoritative
   expiry as HTTP reads, retains its actual Mongo promise for drain, and rejects
   unowned/closed access. Credentials require authenticationVersion 6, a stored
   Passport user ID and fresh FM-015 identity/brand-role validation. A present
   authorization credential retains precedence over session lookup. Native
   persisted-field lookups check own properties.
4. **Admission (P2).** The owned HTTP server intercepts request/upgrade dispatch
   before any third-party wrapper. While admission is closed, requests enter the
   root host gate (including its probes), and upgrades use the shared safe socket
   error writer. Socket.IO client scripts and polling handshakes both return 503
   before activation through the production host. No integration can serve its
   static script around that gate. Readiness exceptions enter the same root
   error writer; upgrade exceptions use its safe socket branch. One-shot readiness
   faults are covered for client scripts, polling and websocket upgrades, as well
   as the existing child-process survival checks.
5. **Upload error guard (P2).** Express and native upload adapters delegate to
   `executeDatastreamUpload`, including validation, authorization, persistence,
   finalization, recovery and the original operation catch. The native reply
   adapter validates JSON serialization inside that guard, as metadata does.
   A circular finalization response therefore preserves the reconciliation
   warning and buffered ETag. An owned multipart counter also observes cancellation
   errors when a staging provider rejects before attaching its own reader;
   this avoids an uncaught stream error without changing the HTTP error envelope.
6. **Grant capacity guard (P3).** Express and native grant adapters delegate to
   `executeProgressGrant`, including the original operation catch and safe body.
   At 10,000 pending grants both return the progress-operation warning, in API1
   and API2, rather than the generic internal-server-error response.

The Express executable still uses `createPortalHost`. Its routes, policy/CSRF
selection, authentication, domain behavior and default Socket.IO close branch
remain in place. Shared-action extraction preserves their HTTP behavior, except
for the deliberate round-2 origin security correction documented below.

## Round-2 review corrections and qualification

**Deliberate Express security fix:** the existing production Express composition
had the same polling-origin bypass as Fastify. Before changing the socket owner,
a real-Mongo 9.0.4 probe used `rawSocketFixture(false, { retainExpress: false })`
to prepare the current production Express application. After a canonical-origin
Engine.IO handshake, foreign-origin POST/GET requests carrying its existing `sid`
returned 200, authenticated a namespace, subscribed to `fm020-record`, and received
`PRIVATE-FM020-ORIGIN-REPRO`. The same sequence succeeded against production
Fastify. `origin-before.json`/`.log` retain those wire observations. This is a
pre-existing security defect, and fixing it on both stacks is the one deliberate
Express behavior change in FM-020; the historical vulnerable behavior is not a
compatibility requirement.

`ProgressSockets.attach` now installs a public Engine.IO middleware during
attachment, before that owner can dispatch a request. It checks the explicit canonical origin for every Engine.IO
request, including initial/existing polling GET/POST and polling-to-WebSocket
upgrades. Invalid, missing and null origins terminate through the shared safe
socket error writer with 403 before namespace/auth/subscription dispatch.
No CORS-only response, second server, listener or persistence client is involved.
The existing initial-handshake admission check and host-wide Fastify admission
gate remain. The middleware is synchronous and starts no asynchronous work;
accepted namespace operations and actual upgraded TCP closure retain their
existing integration ownership.

New production regressions run against **current Express and Fastify**, without
replacing their socket owner. They exercise foreign/null/missing origins before
and after namespace authentication, verify refused packets cannot authenticate,
consume a grant, subscribe/unsubscribe or read queued private progress, and prove
canonical polling and polling-to-WebSocket upgrade still work. The fixture keeps
its immutable FM-019 Express mode for compatibility differentials; selecting the
current mode changes only which production exports the probes instrument.

The repeated-serialization probe reproduced a second `toJSON` invocation for
native upload, grant and metadata responses: Fastify returned generic 500 without
the buffered ETag, while current Express returned 200 and invoked it once.
`json-before.json`/`.log` retain that result. `nativeActionReply.json` and the
metadata adapter now call `JSON.stringify` exactly once inside their action guard
and send the resulting UTF-8 Buffer with `application/json; charset=utf-8`.
Fastify receives bytes, so its serializer cannot revisit the domain result.
Metadata retains serialization before HEAD/freshness handling, then sends no
entity/content type for a fresh 304. Undefined JSON retains empty-body semantics.

The retained/current Express/native differential covers API1/API2 upload, grant,
metadata GET/HEAD/304 and persisted metadata PUT, using stateful `toJSON` values
that succeed once and throw if revisited. It checks exact invocation counts,
normalized wire bodies, UTF-8 byte lengths/content type, ETag preservation and
persisted state. Existing circular-response and operation-error guards remain in
the full raw differential. The new focused cases passed **3 / 0 / 0**
(pass/fail/pending) before qualification.
