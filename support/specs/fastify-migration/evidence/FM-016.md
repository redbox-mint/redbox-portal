## Implementation and scope

- `http/context.ts` provides the agreed public `requestContext` accessor and
  context/actor/brand types. Private request storage is a WeakMap. Explicit brand
  resolution clones/freezes the brand snapshot; actor binding copies only public
  identity fields and clones/freezes only roles for that brand. Context, actor,
  nested brand data, role array and role objects are immutable. Repository and
  session objects are not frozen or retained. Missing/early/unbranded context
  throws; there is no invented default brand or actor.
- `http/language.ts` provides the shared asynchronous language resolver: valid
  query, session, configured language/fallbacks, English, then available language.
  Disabled languages and `cimode` are excluded. Loader and warning failures have
  safe fallback behavior. Session persistence remains an explicit caller action.
- Native `policies.ts` binds the resolved FM-010 route metadata offline, including
  effects before a deny entry. Missing access, missing policy implementations and
  unknown CSRF modes fail composition. Explicit public access remains possible.
  Brand/portal, fresh credentials, branded roles, guest/path rules, browser login
  redirects and record-schema Problem Details preserve current behavior.
- `composition.ts` now requires native security for protected/CSRF declarations
  before application/controller acquisition. It prepares errors/parsers and
  supplied native session/authentication transport, then installs bound security
  before any extra action prelude. The parser/error boundary is also installed
  for a public-only composition without optional security bindings. An extra
  guard cannot bypass core policies or
  CSRF. Action-local validation is deliberately not Fastify JSON-schema validation.
- Native `csrf.ts` accepts only explicit canonical HTTP(S) origins. Forwarded
  host/protocol do not authorize origins. Origin/Sec-Fetch-Site checks precede
  token and API bearer exemptions. Header tokens precede body `_csrf`; query,
  structured and oversized tokens are denied. Comparisons are constant-time.
  Browser bearer/AJAX requests retain token requirements; API exemptions require
  independently verified header bearer credentials. Safe-method behavior is
  selected by each route's recorded mount mode, including TUS checks on all
  methods. Token acquisition persists the native session before publishing bytes.
- Native `validation.ts` reuses executable Zod extractors at each action's explicit
  FM-004 position. It returns action-local validated values without mutating
  request inputs. Native response helpers preserve API version/envelope rules,
  no-cache headers, validation errors, and negotiated Express browser redirect
  bodies, Location/Vary headers and HEAD behavior.
- Native `parsers.ts` preserves ordinary JSON/form parsing before policies:
  strict JSON objects/arrays, empty JSON, supported `utf-*` charsets/BOM, UTF-8 and
  Latin-1 forms, gzip/deflate/Brotli/Zstandard decoding, the 1 MiB inflated bound,
  form key/depth bounds and extended form semantics. Unmatched media types and
  case-insensitive, segment-bounded raw prefixes remain unconsumed. Decoder errors
  become fixed safe parser errors. Aborts dispose decoders; bounded failures drain
  input without destroying the response socket.
- Safe error/observation helpers expose only fixed diagnostics and phase/status
  observations. Provider/domain status, message, body and credential fields are
  never copied to responses or logs. Request/response/error observation, log
  transport, authorization-event and login failure-event rejection cannot replace
  the response. Required login audit failure retains FM-015's session invalidation
  behavior; it is not classified as optional observation. `reply.then` sync/async
  callback errors log only a fixed message, isolate logger failure and release the
  owned lease after logging settles.

The only new dependency edge is an exact **`iconv-lite: 0.7.3`** core pin. This
is the already installed/locked decoder used by the current Express parser, not
an upgrade or new artifact resolution. It preserves UTF-7/UTF-32 and other
recognized `utf-*` input. Root and core lockfiles each add only that dependency
edge; resolved package versions/integrities are unchanged. No install/download
was required. The new dedicated `test:http-security:fastify` command requires a
Mongo URL instead of silently skipping its real-service cases.

### Typed extraction and total error handling

- Internal `http/requestValues.ts` accepts only strings or copied arrays whose
  entries are all strings; scalar consumers accept strings only. Objects,
  functions, numbers and mixed/nested arrays are never coerced. Copying arrays
  prevents their own coercion methods from entering negotiation.
- Native API responses normalize both version-query spellings and the version
  header before calling the existing negotiation helpers. Present invalid values
  become a fixed unknown-version marker, preserving v1 fallback and header/query
  conflict behavior. Validation keeps its distinct string-only header priority.
  Malformed-capture denials use the same safe native response helper.
- Accept negotiation receives only extracted header text. CSRF origin,
  Sec-Fetch-Site, bearer and token values cross explicit scalar checks. Policy
  content-type tests and session proxy-protocol handling also avoid object
  coercion. Native authentication validates credential shape before the identity
  boundary, preserving Express's sanitized 500 for unsupported token shapes;
  session identity and provider error codes no longer use `String(unknown)`.
- Brand/portal captures and login-context selection already enforce string
  types before repository/configuration calls; language selection already ignores
  non-string query/session candidates. The new injected-object tests retain those
  checks. X-Requested-With is not used to grant native exemptions: nested query/
  body values and invalid header values cannot enable one.
- The entire native error-handler body, including awaited response completion,
  is protected. Any internal failure logs only the fixed `HTTP request failed`
  diagnostic, with logging failures isolated, then uses the existing qualified
  `hijack` / raw `writeHead` / `end` APIs to publish fixed **500** JSON
  `{"error":"internal-server-error"}`. It reads no request values and calls no
  negotiation, serializer or session dependency. Its headers/body are literals;
  no caught message, credential or payload is copied. HEAD retains the length
  header and emits no body. An already-ended/committed or failed transport can
  only be closed; failures of that best-effort close are contained too.

No new Fastify public API is allowlisted. The fallback uses the already owned
FM-012 error-handler/hijack/raw-write surfaces. Real-listener injection tests
make the imported negotiation dependency throw while handling a domain failure,
with and without a throwing logger, for POST and HEAD. All require the fixed
response and no secret diagnostics.

### Pinned Fastify escalation and correction

Read the installed **Fastify 5.12.8** `lib/error-handler.js`, `lib/reply.js`, and
`fastify.js` before implementation. `handleError` assigns the next handler's
prototype **before** invoking its function. `preSerializationHookEnd` (including
serializer throws) and `wrapOnSendEnd` call `onErrorHook`, which dispatches a second
error directly to that parent. The negotiated handler's awaited response and local
catch do not intercept that dispatch. Fastify's default parent copies thrown
`status`/`statusCode` and `headers`, logs the caught diagnostic, and ultimately
serializes `message`; leaving it as the parent is unsafe.

`installSafeHttpErrors` now registers two handlers through the existing owned
`FastifyPreparation.setErrorHandler`: a terminal parent, then the negotiated
handler. The parent logs only the fixed `HTTP request failed` diagnostic, with
logging failure isolated, and calls the shared internal `sendTerminalHttpError`.
The negotiated handler's own catch and request ownership's unadmitted-error branch
use the same terminal function. Unadmitted work never invokes prepared application
handlers or creates a brand/actor context.

The terminal function discards all buffered reply/ServerResponse headers using
already qualified `getHeaders`/`removeHeader`, then hijacks and writes fixed **500**
JSON `{"error":"internal-server-error"}`, fixed cache/content headers, an explicit
`Internal Server Error` reason phrase, and byte length **33**. It does not negotiate
or run serializers, session hooks or send hooks, read the thrown error, or copy
request data. HEAD emits no body. Already committed/ended transports only close;
transport and best-effort close failures are contained without re-entering a
Fastify parent. No new Fastify capability, dependency or public export was added.

Same-scope layering uses Fastify 5.12.8's supported default
`allowErrorHandlerOverride=true` and its actual parent-chain implementation.
Fastify emits its fixed `FSTWRN004` registration warning for that layering; the
warning contains no request/error data. It is retained, not suppressed. Upgrading
Fastify requires requalifying these pinned semantics.

### Response ownership and the pinned framework

Re-read Fastify **5.12.8** `lib/error-handler.js`, `lib/reply.js` and their hook
continuations. `handleError()` advances the error-handler prototype before calling
an owned handler. Its default handler imports exception headers/status; its
fallback serializer includes exception messages. `wrapOnSendEnd()` and
`preSerializationHookEnd()` enter error handling after a send failure. Serializer
failures are annotated with `.serialization` before that handoff. The previous
nested handler arrangement could therefore reach the default parent or retain
buffered credential headers and a custom reason after a one-shot normal-response
failure. Merely catching the initial handler invocation does not own these paths.

- New internal `errorBoundary.ts` owns **one** `writeHttpError()` function. Native
  root errors, framework errors, bare HTTP-parser failures, deliberate public
  denials and failed pending responses all enter this function. `HttpFailure`
  carries only fixed `HTTP_REQUEST_FAILED` text and a privately stored trusted
  status. Arbitrary caught values, including `null`, `undefined`, `false`, zero,
  objects and Symbols, become fresh Errors before Fastify can inspect them.
  Native client-input code matching uses own-property checks. Provider messages,
  headers and arbitrary status properties never survive normalization.
- Before output, the function clears buffered headers and restores the standard
  Node status phrase. A deliberate public denial retains only its explicit
  representation/security-header allowlist and credential-free deletion cookies,
  then uses the ordinary native pipeline so existing session persistence and
  public envelopes remain compatible. A fault clears **all** buffered headers,
  invalidates the old send generation, drops its payload, negotiates only the
  bounded safe body, hijacks and writes fixed headers/body directly. Fault output
  never invokes a serializer or send hook, so a repeated failure has no second
  error-response pipeline to attack. Negotiation-dependency failure uses the same
  function's fixed opaque 500. Committed transports close when replacement is no
  longer possible; transport errors never recurse into Fastify's parent handler.
  The fixed `Connection: close` drain instruction is reconstructed explicitly
  after clearing headers; no arbitrary buffered Connection value is retained.
- `router.ts` installs the root boundary and intercepts sends before admission,
  including probes and early denials. Ownership shares its submission/generation
  state. A pending-response error replaces the pending payload through the same
  writer. Duplicate normal sends are discarded with a fixed diagnostic.
- `requestOwnership.ts` owns outgoing hook continuations once, retaining their
  original asynchronous work while preventing Fastify from independently
  resuming stale promise continuations. A replaced, hijacked or committed send
  cannot resume. Synchronous/asynchronous exceptions and native continuation
  failures are normalized. Post-send exceptions/rejections and duplicate returns
  are contained with fixed diagnostics; the original exception never reaches a
  native logger. Callback leases and custom owned error handlers remain covered
  by the retained FM-012 checks. Normalized Errors remain mutable because the
  pinned serializer annotates them; freezing them would itself create an uncaught
  annotation failure.
- Removed `terminalError.ts`, the second negotiated/terminal handler arrangement,
  obsolete 25-case R4 test group and redundant per-log-call transport catches.
  `responses.ts` now holds public response helpers and isolated observation hooks;
  it does not register another error writer.

### Diagnostic ownership

New internal `logging.ts` supplies the **only** `loggerInstance` used by Fastify.
Its instance/request/reply/child loggers share frozen methods. Unsafe native
logger options/bindings are discarded, request logging is disabled through the pinned public `LogController` API, and the
sealed request/reply views deny logger replacement before even their first lazy
logger read. The wrapper accepts native internal warnings as well as owned calls.
It emits only frozen `{code, level, path?}` records: known fixed codes or
`HTTP_DIAGNOSTIC`, plus an optional string path with query/fragment removed. It
never formats arbitrary messages, exception messages/stacks, headers, cookies,
bodies or logger bindings. Sync transport throws and async rejections are
swallowed and counted in private logger statistics. The default host sink passes
only fixed warning/error/fatal codes to the application's logger. Existing
observation callbacks still receive only their fixed public events/messages and
remain independently failure-isolated.

### Recovery, fallback and operator contract

The shared `createHttpLogger` boundary now handles sink throws/rejections and
stream/worker events through the same degraded-state transition. It retains
crash containment and discards the original error. Normal diagnostics are dropped
while degraded; there is no buffered-record queue or replay of request data.
A single in-flight recovery probes a destination after **100 ms**, doubling
failed-attempt delays through **200, 400, 800, ...**, capped at **30 seconds**.
Successful recovery resets the delay, clears degradation and resumes ordinary
redacted writes. The probe itself is a fixed `HTTP_LOG_RECOVERY` warning with no
request fields. It awaits asynchronous sink settlement and one I/O turn, then
requires no intervening destination failure and an available destination graph.
A destroyed/ended stream, exited Worker or disconnected pipe is not mistaken for
a successful delivery just because an upstream write accepted buffered bytes.

The boundary retries recoverable destinations in place and invokes supported
file destination `reopen()` methods when unavailable. An optional internal
`HttpLogTarget.reopen` factory allows the application to replace an arbitrary
failed stream/transport; the returned graph is contained before the first write.
The factory survives replacement for subsequent faults unless its replacement
supplies a new factory. Late events from retired destinations remain contained
but cannot degrade their healthy replacement. The application owns acquisition
and closure of borrowed destination resources; core does not clone arbitrary
transports or close the application's logger. A destination requiring replacement
without a supplied factory remains degraded, with capped retries and the operator
signal, until its owner repairs/replaces it. There is no permanent silent-disable
state and no unbounded retry frequency.

While degraded, the boundary writes only one fixed line per failure class per
**30-second** window to stderr: `HTTP_LOG_SINK_FAILURE`,
`HTTP_LOG_STREAM_FAILURE`, `HTTP_LOG_WORKER_FAILURE`, or
`HTTP_LOG_RECOVERY_FAILURE`. The rate limit belongs to the sole host logger and
has only those four keys. A synchronous fd-2 write avoids an asynchronous stderr
stream `error` event; a failed fallback write is swallowed and counted without
recursive logging. Neither exception text, headers, bodies, URLs nor any request
value can enter the fallback. Recovery timers are unreferenced and cancelled by
quiesce; an already-started attempt remains owned through settlement.

`FastifyHost.status().logging` exposes only fixed numeric/boolean instrumentation:
`degraded`, `failures`, `diagnostics`, `dropped`, `recoveryAttempts`, `recoveries`,
`fallbackWrites`, `fallbackFailures`, and `pending`. This status never influences
`ready`, admission, the host failure phase or liveness. Exact global GET
`/healthz` preserves `{healthy}` while there has been no logging failure; after
any logging failure it additionally returns the same `logging` snapshot, including
`degraded:false` after recovery and cumulative counters. `/readyz` retains the
exact `{ready}` body and all FM-011 readiness rules. Logging loss alone leaves
both probes **200** on an otherwise healthy activated host. HEAD, aliases,
root-context prefixes, early/unbranded requests and prepared-domain-hook bypass
remain unchanged; no fabricated context is created.

**ACCEPTED-LOGGING-HEALTH-SIGNAL** records the round-7 orchestrator decision to
add the fixed `logging` member after a fault. This is an explicit, narrowly scoped
addition to [FM-011's probe/status contract](FM-011.md#implementation) and
[design section 10's lifecycle contract](../design.md#10-host-lifecycle-and-ownership),
not a readiness dependency or a new endpoint. The retained raw HTTP status test
asserts the pristine health body, degraded health/counters, exact readiness body,
200 status throughout, and the recovered signal. The strict host-survival harness
also validates the optional signal and prohibits secret text.

### Sink lifetime and shutdown ownership

Every asynchronous sink result is retained in the logger's pending set and the
current HTTP request lifetime when one exists. Host-bound sink invocation also
runs in an accepted persistence scope, so writes after an await remain authorized
while shutdown waits, including diagnostics emitted outside a request. Recovery
factories and probe writes execute in their own accepted application scope and
share the same pending-work accounting. Public logger methods remain synchronous
void-returning capability methods; no callback registration or promise factory
is added to the FM-012 public preparation/request API.

The registered HTTP resource quiesces future recovery and drains accepted request
work, then seals new sink dispatch and awaits every outstanding logger promise
before application dependency closure. Post-send and callback-error diagnostics
are included; callback-error logging explicitly re-enters its still-owned request
context before releasing the callback lease. Caller stop deadlines still reject
without cancelling work or authorizing resource closure; retry joins pending
work, then closes resources once settlement permits it. Late framework diagnostics
after the drain barrier are dropped instead of touching closed borrowed resources.

Retained tests live in `loggingSurvival.test.ts`, already selected by the security,
focused host/routes, explicit survival and default full-core suites. New coverage
includes real Pino transient stream recovery, disconnected-pipe repair, exact
capped retry times over **100 seconds** of simulated time, per-class fallback
rate limits, broken fallback fd isolation, sync/async replacement factory failure
and later repeated recovery, retired-source events, raw HTTP status/health/
readiness, and **12** held-sink shutdown cases: request, post-send, synchronous
and asynchronous callback failure, outside-request diagnostic and recovery,
each fulfilled/rejected. Every held sink verifies a borrowed resource stays open,
performs its final accepted persistence operation after a stop deadline, and
allows closure only after all started sinks settle. No log-secret coercion or
process-wide exception/rejection suppressor is introduced.

### Destination state and application-owned recreation

The logging boundary observes **error**, **close**, **finish** and Worker exit,
and checks the entire pinned destination graph before **every ordinary dispatch**
and when status is read. A latched destination fault, `destroyed`, `closed`,
`errored`, `writableErrored`, `writable === false`, `writableEnded`,
`writableFinished`, an exited Worker or lost pipe connection marks logging
degraded before any further write. Diagnostics are dropped and counted in that
state. Only fixed, rate-limited failure-class lines can reach stderr, with the
round-7 rate limit and fallback-failure containment retained. Logging degradation
never changes admission, liveness or readiness; the existing optional health
signal and status counters remain governed by **ACCEPTED-LOGGING-HEALTH-SIGNAL**.

Recovery requires an explicit application-owned factory. No factory means no
in-place retries or pretend recovery: the degraded signal stays visible, dropped
counters rise, and fixed fallback continues on subsequent diagnostics within its
rate limit. With a factory, attempts remain single-flight at **100, 200, 400,
... ms**, capped at **30 seconds**, with no replay queue. A replacement graph is
contained before use. Backoff and degradation reset only after the fixed probe
is confirmed by that destination and its graph remains healthy. A factory with
streams must supply an explicit confirmed probe; a stream-free async sink's
settled write is its delivery contract. Merely accepting bytes or waiting an
I/O turn cannot report a recovery.

`applicationLogging.ts` wires the default Fastify composition to internal creation
recipes recorded by ReDBox's existing `createPinoLogger` and
`createNamespaceLogger`. Stdout/stderr and known SonicBoom file settings recreate
through the same logger configuration, including level, namespace/prefix and
file options. Async file identity is read after the original open has populated
it, rather than assuming it exists at construction time. The default logfmt
transport recreates the same target/options with an opt-in, fixed delivery
acknowledgement for the HTTP recovery probe.

SonicBoom **drain** confirms the probe's OS destination write. The owned logfmt
replacement emits ThreadStream's supported `EVENT` acknowledgement only after
its actual SonicBoom destination drains; an upstream ThreadStream flush does
not count. Both paths reject on error/close/finish and bound an unconfirmed probe
at **1 second**. This is delivery confirmation, not an fsync/durability promise.
A full device or permanently broken pipe can never increment `recoveries`.
Pino's EPIPE filter replaces instance `destroy` with a no-op; owned replacement
cleanup uses SonicBoom's qualified prototype closure so failed file descriptors
are still released. Worker replacements are terminated through their owner.
Only factory-acquired resources are closed; the original parent logger remains
borrowed. Factory/probe/closure and async sink promises remain in the accepted
application/request drain; stop deadlines do not cancel borrowed sink work.

The shared configuration changes record only private weak creation provenance.
They do not replace/wrap the Express logger, change its arguments, formatters,
levels, hooks, destinations, standard logfmt branch, or error behavior. The
logfmt delivery branch is enabled only on Fastify-owned replacements. No Express
mount, action, middleware or host changed. Its retained production characterization
still exercises the existing failing-destination outcomes. Arbitrary opaque
custom transports still require an owner-supplied recipe/factory; they remain
visibly degraded when one is unavailable. A factory cannot repair a physically
lost stdout reader or a persistently full device; those nodes remain ready with
logging-degraded status and fixed fallback.

No Fastify preparation/request capability is added. Recipe, probe and owned
cleanup functions are internal composition resources; their work uses the
existing FM-012 accepted-work/drain boundary. No process-wide exception or

## Round-9 correction — remove automatic recovery; observe explicit destinations

The round-9 orchestrator decision supersedes all automatic-reopen, retry/backoff,
probe/acknowledgement and recovery-counter behavior in rounds 7–8. Logging failure
now latches degradation until **operator restart**. There are no replacement
factories, stream-close waits, recovery timers, recovery writes or replay queues.
The [design-facing logging note](../logging.md) records the final contract.

All four findings were verified in the prior implementation: a different Pino
copy's private stream symbol could hide its destination; a failed async SonicBoom
open could never satisfy the replacement-close wait; shared creation dereferenced
`destination.constructor.name`; and recreating a logger from its original recipe
could lose runtime/namespace levels. Removing recovery eliminates the latter two
recreation paths; shared creation no longer inspects constructors.

### Final implementation and regression scope

- `logging.ts` observes concrete destination objects, their multistream/pipe sinks
  and transport Worker events. No Pino-private symbols are imported or inspected.
  Sources supplied through `FastifyHostOptions.logger` are the explicit boundary
  for external Pino copies. Shared ReDBox loggers expose only their concrete
  destination through a small private weak association; their namespace children
  inherit that association through ordinary JavaScript prototypes.
- `log.config.ts` retains the destination it passes to Pino. For the default
  logger it constructs the same public logfmt transport explicitly and passes it
  as the destination, permitting observation without Pino internals. This hook
  installs no listeners and changes no formats, serializers, level hooks, custom
  levels, namespace construction or runtime settings for Express. There are no
  destination type/constructor checks or recreation recipes. The shared
  `logfmt-transport.cjs` is restored **byte-for-byte to 00511d68b**; its special
  Fastify delivery acknowledgement is removed. `applicationLogging.ts` is deleted.
- Before every diagnostic and status read, failed state is checked. Error, close,
  finish, Worker exit, destroyed/errored/non-writable state or a lost pipe latches
  failure. Later diagnostics are dropped and counted. Fallback is at most one
  fixed-code line per failure class per **30 seconds**, using a contained fd write
  with no exception, URL, credential, header or body interpolation.
- Existing status/health exposes degraded state and failure/drop/pending/fallback
  counters under **ACCEPTED-LOGGING-HEALTH-SIGNAL**. Readiness remains **200**.
  Recovery fields are removed with the removed feature. Repairing a destination
  in place does not clear degraded status; operators restart the node.
- Accepted async sinks remain in request/application drain until settlement.
  Existing stop deadlines still bound caller waiting without releasing borrowed
  work. Host shutdown neither closes nor waits for closure of borrowed streams,
  so an unopened file destination cannot hang host cleanup.
