## Implementation and boundaries

Selected **direct provider bindings**, as allowed by design Q25. Source inspection
of the actual portal composition and all Passport `use` sites found exactly local,
bearer/API token, AAF JWT and OIDC (including named/configured providers). There is
no additional first-party strategy to omit.

- [Native authentication](../../../../packages/redbox-core/src/http/fastify/authentication.ts)
  binds the existing account/identity operations to owned native hooks/routes.
  Actors live in an application-local WeakMap. The session version gate runs
  before deserialization; identities and roles come from authoritative user reads.
  Explicit Authorization headers retain precedence over session authentication,
  including malformed/invalid bearer credentials. Existing body/query token lookup,
  duplicate-token rejection and session-first behavior without that header survive.
- [Provider bindings](../../../../packages/redbox-core/src/http/fastify/identityProviders.ts)
  own their OIDC configuration map and AAF key configuration per application.
  They call the same `AuthenticationAccounts` domain for mappings, email rules,
  hooks, linked/disabled accounts and provisioning. OIDC uses openid-client
  discovery/configuration, S256 PKCE, session-bound one-use state, code exchange,
  claim validation and userinfo. AAF uses jsonwebtoken verification with the
  current issuer/audience/algorithm/expiration/not-before/clock-tolerance options,
  including asynchronous signing-key callbacks.
- Native login regenerates the session, saves the serialized identity, then saves
  authentication version **6**, validated brand/portal and allowlisted provider
  logout URL before awaiting the required audit. A failed save/audit destroys the
  replacement and clears the credential. Logout clears/saves identity, regenerates,
  destroys, awaits audit and clears the cookie before redirect. Provider logout
  only uses configured origins. API tokens never create authenticated sessions.
- The retained user-version behavior is the existing numeric session
  `authenticationVersion === 6` plus fresh user/role/disabled/link resolution on
  each request. Current Express has no separate per-user version field; none was
  invented for this task. FM-014 namespace/generation revocation is retained.
- Success/failure chronicle fields and required login/logout/failure callbacks
  remain explicit. Failure events select bounded usernames and never copy
  credentials/assertions/token responses. Required audits persist in real Mongo.
  `RequestChronicleHelper.existing` now accepts an object at its type boundary;
  its lookup implementation and Express behavior are unchanged.

No Express request/response facade, middleware bridge, Passport emulation, raw
Fastify recovery or new public Fastify API was added. The existing seal already
qualifies the hooks, content parser, routes, reply headers/redirects and Session
methods used here. The preparation/requestOwnership allowlists are unchanged.
Route/hook promises own provider work; the asynchronous AAF key-provider return
is explicitly request-retained. Real disconnect tests exercise these adapters.
The cookie serializer is the existing synchronous @fastify/cookie function,
used through the qualified header API.

Production Express composition/providers/routes, default executable, public
barrels, session implementation and task checkboxes are unchanged. The sole
Express identity import in the new runtime is type-only and erased by the build.
The new internal route binder is the P2 qualification composition. FM-016 still
owns the complete native context/policy/CSRF/parser/error pipeline; its CSRF guard
is an explicit input, with a no-op only in the auth-only fixture. No FM-016 or
later-task completion is claimed.

`jsonwebtoken: 9.0.3` and `accepts: 2.0.0` are promoted from already-installed
dependencies to exact direct core dependencies for verification and matching
HTML/JSON negotiation. Both lockfiles are updated. Lockfile-only installs ran
serially under 180-second timeouts at core and root. Unrelated root metadata churn
was discarded; negotiator retains the already-locked **1.0.0**. A package-name /

## Retained differential and provider fixtures

- [Differential](../../../../packages/redbox-core/test/http/fastify/authenticationDifferential.test.ts)
  executes the same scripts against the unchanged Express middleware/provider/login
  stack and the native bindings, serially with separate disposable databases.
- [Shared fixture](../../../../packages/redbox-core/test/http/fastify/authenticationFixture.ts)
  supplies the same real repositories, account domain, profile mappings, hooks,
  configured context, security-event collector and persisted audits to each host.
  The existing Mongo fixture gains an optional offline pre-initialize callback so
  the Fastify host is registered before application initialization. Its default
  Express behavior is unchanged. The controller typecheck root includes source
  because this shared fixture imports the actual source composition.
- [Local OIDC server](../../../../packages/redbox-core/test/http/fastify/oidcFixture.ts)
  serves real HTTP discovery, authorization, token, JWKS, userinfo and logout
  endpoints. It checks client credentials, response type, redirect binding,
  one-use authorization codes and actual SHA-256 PKCE verification. It signs real
  RS256 ID tokens with a fresh local RSA key. No library discovery/grant/claim/
  userinfo operation or account mapper is mocked. The code/claim validation policy
  is the same openid-client policy as Express; no extra signature-policy claim is
  made beyond that stack. Denial/error/issuer/audience/expiry/subject controls use
  real protocol responses. Token exchange can pause on the actual HTTP request.
- AAF fixtures are real locally HMAC-signed assertions with configured verification,
  not fabricated parsed profiles. Tests include bad signature, algorithm, expiry,
  issuer, audience, subject/attribute mapping and email denial. Defaults retain
  Express's `ignoreNotBefore: true` and 120-second tolerance.

This uses FM-005's local signed-AAF mapping and the task's expressly allowed
in-process OIDC alternative. It does not relabel the historical fixed-port
Keycloak/Bruno fixture as executed. Dynamic issuer/callback ports are reserved
serially and released. Named-provider selection is returned as an OIDC response
parameter by the local IdP; redirect_uri itself stays query-free because the
selected openid-client strips response query parameters during token exchange.
Both hosts use this identical flow and enforce exact redirect/PKCE binding.

The differential normalizes only independently generated Mongo user/role/brand
IDs, observation timestamps, random session-cookie values, and local fixture
origins/encoded callback ports. Cookie attributes, statuses, bodies, profile
fields, role membership, redirect destinations, failure events, audit effects,
session counts and provider-call counts stay comparable. Positive assertions
also require actual success, mapped attributes, rotation, revoked cookies and
completed audits, so equal denials cannot qualify a successful provider.

Coverage includes local credential bounds/custom nested fields/query fallback,
empty-field fallback, string-only OIDC scope defaults/static endpoint parameters,
fresh password/token resolution, mapped profiles and awaited hooks, identity
replacement rejection, linked/disabled/orphan/cyclic users across all providers,
brand denials, session-version invalidation, explicit bearer precedence, token
sources, cookie rotation/logout revocation, allowed provider logout and disabled
provider logout, HTML/JSON rejection negotiation, form submissions, and HEAD
session/version ordering. OIDC additionally covers discovery and metadata-object
configuration, named providers, claims/userinfo sources, state/session mismatch,
code replay, provider denial/token/userinfo failures and malformed claims.

Real client-abort/stop-deadline/retry cases cover local/AAF login audit, bearer
credential resolution, AAF signing-key callbacks, OIDC login audit, and the actual
OIDC token exchange for both allowed and denied accounts. They require a deadline
failure with retained Prisma clients, then successful completion/retry with zero
clients and exact audit effects. Separate live native applications prove that
keys, identities, sessions, OIDC issuer/configuration and handshake state do not
cross application boundaries or depend on the other application's lifetime.
