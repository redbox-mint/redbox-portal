## Round-1 reviewer remediation

The P2 race finding is addressed in `MutationLifecycleMongo.test.ts` and the new
`mutationRaceSupport.ts` fixture. No production action, guard, persistence or
retained domain behavior changed in this round; a comparison with the preceding
FM-026 source archive confirms every other implementation file is unchanged.

The fixture wraps the already initialized production record/dashboard owners and
real storage/repository methods, using bounded gates and request-local participant
tracking. Both requests perform their real reads and real Mongo persistence.
Neither snapshots, CAS outcomes, authorization decisions nor HTTP results are
substituted. Winner and loser use distinct canonical save-request UUIDs. The gates
fail within eight seconds, release in `finally`, join pending HTTP requests and
restore all probes before fixture cleanup.

Record cases force three schedules for every concurrency-capable declaration and
both API versions:

- `claim-held-through-conflict-response`: both requests reach persistence using
  the original authority. The winner commits its first real claim and is held
  there while the loser attempts CAS, rereads conflict authority, decides the
  conflict, performs response authorization/projection and completes its HTTP
  response. Only then may the winner finalize.
- `winner-settled-before-loser-cas`: both reach persistence from the original
  authority; the loser cannot dispatch CAS until the winner's complete HTTP
  response has arrived. All loser conflict reads and decisions see settled state.
- `winner-settled-before-response-projection`: the loser loses CAS and finishes
  its domain conflict read/decision while the winner's claim is held. The winner
  then finishes before the loser returns to the action's authority reread and
  response projection. The trace snapshots the domain decision before projection
  can mutate the result, and asserts the two response orderings.

Dashboard cases force `validation-after-winner`, `save-read-after-winner` and
`cas-after-winner`: respectively the initial validation revision check, the second
save revision check, and a real Mongo CAS failure. Copy has one authority read,
so it uses the first and third schedules. This pins the existing different
conflict messages and current/expected-revision fields instead of assuming any
409 body is interchangeable.

Every schedule compares the winner AND loser in full: status, all existing
normalized response headers (including ETag), body, and complete selected Mongo
rows/queue payloads. Missing/stale record precondition responses and dashboard
retry responses also remain compared. The established normalization removes only
volatile identities/times/session facts; fixed-record ETags, versions, conflict
problems and response metadata are retained. The archive includes original raw
HTTP responses as well as the normalized comparisons and stage traces.

Each race run exercises **114 record schedules** (19 declarations × two versions
× three schedules) and **32 dashboard schedules** (four save declarations × two
versions × three schedules, plus two copy declarations × two versions × two
schedules), for **146 schedules across each of three transports**, **438 race
pairs / 876 winner-and-loser responses**. These are two aggregate Mocha tests;
the per-schedule counts are separately audited from the observation reports.

This is purely an interleaving difference already present in retained Express.
The retained adapter already contains the same post-conflict authority reread;
no migration authorization regression was found. For both API versions and both
purge declarations, all three transports give these forced outcomes:

| Schedule                                  | Winner | Loser | Loser ETag / authority                                                                                             |
| ----------------------------------------- | -----: | ----: | ------------------------------------------------------------------------------------------------------------------ |
| Claim held through conflict response      |    200 |   412 | Revision 3 tag; `purge-pending` tombstone remains observable                                                       |
| Winner settled before loser CAS           |    200 |   403 | No ETag; active record and tombstone are absent                                                                    |
| Winner settled before response projection |    200 |   403 | Domain first decides stale revision from revision 3; the action then rereads absent authority and removes the ETag |

The third schedule proves the precedence directly: an existing domain conflict
can become the safe `not-authorised` response when the later action reread can

"Pre-existing issues (deferred)" below, without changing it.

## Implementation

Five retained Express adapters now use the same named transport-neutral actions
as the new native controllers. The record save pipeline still owns domain
checks, authorization, workflow transitions, optimistic concurrency, schema
references, record revisions, audit, indexing, hooks and trigger jobs. No
persistence, idempotency or cancellation policy was added to a transport.

Native controllers inherit already migrated read/metadata controllers; the
production selection supplies one concrete binding per controller. The combined
record factory also exposes the existing raw upload action when selected.
`portalMutationHttpInputs` borrows initialized production owners through lazy
getters and forwards the existing configuration. No parallel owner or resource
acquisition was introduced.

The host derives mutation ownership from final resolved executable targets,
including aliases. Its pre-validation prelude uses the existing shared actor
and administrator guards, preserves configuration envelope/retired-route ordering,
and normalizes Express wildcard arrays before Zod. The existing FM-025
session-aware empty-denial framing hook now includes mutation declarations. The same guards run inside
shared actions for Express and direct action use. All native actions reuse the
existing guarded JSON serialization/submitted-response boundary.

## Differential and lifecycle method

The five immutable Express adapters are loaded from the starting commit with
`git show`, hashed and installed only while the production Express host prepares
its registrations. Each original mount must run exactly once. Refactored Express
and native Fastify use the production application, resolved installation and
host. There is no fixture action dispatch replacement. Mongo and Solr are real,
disposable services; session login and bearer actors use production identity.

The route matrix compares raw HTTP status, headers, body, complete selected
Mongo rows and real queue job data between retained Express, current Express
and Fastify. Original content length is checked against original bytes, then
compared using normalized bytes. Generated record IDs, their bound ETags,
internal save-reference identities, session cookies, request/execution identities
and timestamps are normalized; authorization, schemas, revisions, effects,
problem bodies, configuration fingerprints and job payloads are compared.

The matrix has 4,536 route cases: 54 new declarations × two API versions ×
38 default-policy scenarios, plus the same declarations and versions × four
reduced-policy scenarios. Each case has three transport observations. Scenarios
cover session/bearer/anonymous/missing actors, role and brand refusal, CSRF/origin,
malformed parsing, Zod extraction, nested/duplicate query input, aliases/arrays
and header precedence for API version, schema/precondition conflicts, missing
and private objects, typed domain refusals, generic failures and serialization
failures. Invalid-body cases also combine auth, brand, CSRF and missing-actor
failures to pin precedence. Reduced policies select only `noCache` and
`brandingAndPortal`.

Six lifecycle checks cover combined native raw/read/write composition, every
non-create record mutation under strict policy and real Mongo races, workflow
transitions and revision/history/schema references, dashboard save/copy revision
races, accepted configured actions after disconnect, and real synchronous and
detached hooks, queued triggers, audit, Solr and HTTP side effects across client
disconnect and a failed-then-retried stop deadline. The existing one-second audit
grace is deliberately allowed to expire while the second detached hook is held;
audit/index workers settle before queue claims quiesce, and executing trigger
work remains held across the stop timeout. Conditional retries cannot re-enter
hooks; tracked-harvest retries cannot add records, audit or jobs.
