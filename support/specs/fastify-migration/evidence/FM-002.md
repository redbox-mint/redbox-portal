## Frozen names, access and HEAD

Missing core names use the existing replacement identity:

```text
core-http-${lowercase method}-${first 16 hex SHA256(canonicalHttpRoutePath(runtimePath))}
```

`runtimePath` applies the two actual adapter translations, `:key*` to `*key` and
`datastream*` to `datastream{*tail}`. The original spellings remain in `original`.
Canonicalization comes from the current extension resolver. All 152 API names
therefore agree with already-exposed core replacement names. Named extension
routes remain verbatim; the published example remains **`example-health`**.

An ALL declaration receives a deterministic `core-http-all-…` collection name
for this inventory. Its `replacementTargets` contain the seven existing
method-specific API1 reservation names; the synthetic ALL name is not an API1
replacement alias. Router ALL behavior is broader than those seven reservations;
other-method network behavior remains characterization work in FM-003.

Current access representations are intentionally distinguished:

- Core API `policy` names, when present, precede the most-specific configured
  action/controller/global mapping. `true` is the configuration's explicit public
  mapping; `false` appends a denial. The generator calls the real
  `resolveEffectivePolicies`, retaining ordered effects such as `nocache` before
  denial. API `security`/role documentation is not runtime authorization.
- Default `portalHttpPolicies()` is the captured profile. Programmatic
  `PortalHttpOptions.policyConfiguration` overrides require their own resolution
  and qualification; no institution-specific override profile was invented.
- Public page declarations still retain their mandatory brand/actor/path checks.
  A configured `true` does not remove those checks. Runtime domain authorization
  remains additional to the recorded named chain.
- Extension API1 uses literal `access: 'public'` or a non-empty ordered policy
  array. Naming `csrf` in that array invokes `apiProtect`. Global middleware
  stages do not inherit a route access declaration.
- API declarations commonly say `csrf: false`, while adapter mounts apply
  `apiProtect`: canonical-origin checks plus verified-bearer exemption or the
  session synchronizer. The inventory records both. The GET
  `refreshCachedResources` action also applies `apiProtect`; method alone does
  not determine CSRF. TUS applies it on ALL methods, including HEAD/OPTIONS.

HEAD and dispatch details preserved from source and existing assertions:

- `/user/begin_oidc` has explicit HEAD action `disallowedHeadRequestHandler`,
  returning 405; its frozen identity is **`core-http-head-e3ee2548904017ea`**.
  The GET row points to it and does not claim the HEAD replacement target.
- The three administration GET declarations (`/api/admin/refreshCachedResources`,
  `/api/admin/config/:configKey`, `/api/admin/config`, under the brand/portal
  prefix) explicitly deny HEAD inside `mountAdminOperationRoutes`, returning
  **405 with `Allow: GET`**. Effective policies run first; refresh also runs
  `apiProtect` first. The denial precedes request context, administrator/domain
  checks, validation and action work. These are GET-owned HEAD policies, so their
  existing HEAD replacement reservations remain attached to the GET rows.
- Font delivery explicitly validates the brand/hash and reads verified or cached
  bytes before a conditional 304 or HEAD 200 with font metadata and no body.
  Its row references `BrandingDelivery` and `BrandingFontDelivery.test.ts`.
- Installed extension HEAD policies precede implicit GET handling regardless of
  declaration/provider order. Existing `head-routes.test.ts` checks public GET
  `read` versus protected HEAD `headers` in both orders and both compositions.
  Those fixture names are unchanged; they are not installed production routes.
- Both attachment download GET aliases run policies, then call `next()` for HEAD,
  reaching the corresponding TUS ALL mount. Each declaration keeps its own
  owner; this is ordered fallthrough, not an intentional route replacement.
- The actual host intercepts exact GET `/healthz` and `/readyz`, outside root
  context and ordinary admission. HEAD is not intercepted. The old offline
  owned-route manifest nevertheless reserves health HEAD identities. The tests
  preserve those existing reservations while the supplemental records describe
  actual dispatch. FM-003/FM-010 must resolve this distinction explicitly.
