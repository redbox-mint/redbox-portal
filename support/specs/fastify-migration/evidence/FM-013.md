## Internal composition and real-listener proof

[`composition.ts`](../../../../packages/redbox-core/src/http/fastify/composition.ts)
joins the existing stages without adding a host selector, extension loader or
security implementation:

1. FM-010 `composeRoutes` normalizes declarations, resolves access metadata and
   rejects policy/collision errors offline.
2. FM-009 `composeControllers` validates concrete bindings and the normalized
   routes' declared action targets, still without constructing controllers.
3. Only after those checks succeed is one FM-011 `FastifyHost` constructed.
   Its owned preparation stage constructs the selected controller instances
   **after application initialization**, installs the FM-010 plan through the
   FM-012 sealed registration capability, awaits readiness, then listens.
4. Activation, request ownership and deadline/retry cleanup use the existing
   host and application protocols. There is no second listener, lifetime owner,
   close adapter, service locator or public export added by FM-013.

[`composition.test.ts`](../../../../packages/redbox-core/test/http/fastify/composition.test.ts)
exercises the existing real
[`ApplicationStatusController`](../../../../packages/redbox-core/src/http/controllers/ApplicationStatusController.ts),
with its exported concrete input and declared `status` action. The prototype
declares `GET /application-status`, stable name `internal-application-status`,
under `/prototype`. The only guard is explicitly public with no CSRF or named
policies; it asserts that metadata. This does not qualify the FM-016 pipeline.

All **14 tests** use actual listeners/HTTP or negative pre-listen composition;
none uses Fastify injection. Controlled promises and bounded socket waits port
the relevant assertions from the existing host/request-lifetime suites:

- No listener or controller construction during blocked application
  initialization. Exactly one controller construction after initialization and
  before the one listen call; concurrent initialize/activate calls join.
- GET/HEAD/POST/OPTIONS receive the existing 503 admission envelope while
  activation is held, without invoking the controller. Global health stays live
  and readiness stays false. Activation admits real status responses, including
  case-insensitive/trailing-slash matching. Implicit HEAD invokes the declared
  action and retains content length; OPTIONS reports `GET, HEAD`. Unprefixed and
  helper paths return 404. Successful stop is idempotent and the port refuses TCP.
- Missing binding/controller, unlisted action, unknown policy and effective
  case/slash collision fail before host registration, application-module
  acquisition, controller construction or listen. A non-callable selected action
  fails after initialization, before listen, and cleans acquired modules.
- Stop during initialization exceeds its caller deadline without releasing the
  held module; release and retry finish cleanup without constructing a controller.
- A concrete status subclass exercises five lifetime cases through this same
  declared-action composition: returned work after an early response, explicitly
  tracked work after a response, a disconnected pending action, an asynchronous
  `reply.then` callback, and a pending store-callback seam after disconnect.
  Transport closes once while the held work remains owned. Stop reports its
  deadline, retains the borrowed module and accepted HTTP/persistence contexts,
  then retries successfully after the pending operation completes. The store seam
  is controlled callback work, **not native session or real-Mongo session proof**.
- A failed consumer close retains its explicitly declared dependency. Retry closes
  consumer then dependency, with only one native transport close and idempotent
  success. Transport completion does not imply application cleanup completion.

## Observed Fastify 5.12.8 readiness and close semantics

These are observations of the pinned dependency, not promises inferred from an
API name. FM-013 reruns the tests that pin them:

| Actual behavior | Executable regression reference and consequence |
| --- | --- |
| `ready()` boots the queued nested plugin graph and waits for asynchronous `onReady`; no listener is needed. Plugin/onReady rejection is an initialization failure. | [FM-011 host tests](../../../../packages/redbox-core/test/http/fastify/FastifyHost.test.ts), “initializes the application, prepares the complete plugin graph, then binds exactly one server” and the plugin/ready failure controls. All three held startup barriers refuse real TCP before listen. |
| Closing can itself boot queued plugins. Interrupted/failed prepare cannot allow their acquisition to race dependency cleanup. | [FM-012 close tests](../../../../packages/redbox-core/test/http/fastify/FastifyClose.test.ts), “owns queued plugin initialization after prepare failure/interrupt/plugin-failure”. The host joins readiness and retains partial acquisition after deadline. |
| `listen()` resolves before asynchronous `onListen` work finishes. | [FM-012 pinned semantics](../../../../packages/redbox-core/test/http/fastify/FastifyClose.test.ts), “resolves listen before asynchronous onListen work”. The sealed preparation allowlist rejects unqualified `onListen`. |
| Close order is `preClose`, native server close, child `onClose`, then root hooks in reverse registration order. A second successful native close does not repeat hooks. | [FM-012 pinned semantics](../../../../packages/redbox-core/test/http/fastify/FastifyClose.test.ts), “closes the listener before onClose and runs child hooks before root in reverse registration order”. Shared domain/pool cleanup belongs to the application graph. |
| A rejecting `onClose` rejects the first native close, but a second raw Fastify close resolves without retrying the consumed hook. | [FM-012 pinned semantics](../../../../packages/redbox-core/test/http/fastify/FastifyClose.test.ts), “does not rerun rejected onClose hooks on a second raw Fastify close”. The host retains the first close promise and its failure. |
| Fastify discards a native `server.close` callback error. | [FM-012 pinned semantics](../../../../packages/redbox-core/test/http/fastify/FastifyClose.test.ts), “discards server.close callback failures”; the host's native-error observer preserves it. The `onClose`/`native-close` irrecoverable-failure controls retry remaining application cleanup while continuing to reject host stop. |
| With `forceCloseConnections: false`, idle keep-alive sockets can be reaped while active/partial connections and retained application work need their own drains. | [FM-012 socket/lifetime controls](../../../../packages/redbox-core/test/http/fastify/FastifyClose.test.ts), “reaps idle keep-alive sockets”, “finishes an in-flight response”, and “retains a partially received owned connection”; [FM-013 composition tests](../../../../packages/redbox-core/test/http/fastify/composition.test.ts) establish the same separation for declared actions. |
