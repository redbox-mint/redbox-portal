## Ownership and implementation

The host owns one Fastify instance, its one prepared underlying HTTP server, one
stored transport-close promise, admission, and its opt-in signal handlers. Node's
HTTP server owns ordinary connections; application integrations own their upgraded
sockets/streams and register drain/close with the existing application registry.
No second listener, socket registry, dependency container, signal owner, or
application-stop `onClose` hook is introduced.

Stop closes admission and quiesces synchronously. Concurrent callers receive the
same attempt promise. It awaits raw initialization/preparation/activation work
within the caller's absolute deadline before beginning transport or application
cleanup. Expiry keeps partially acquired collaborators owned; settling that startup
work does not automatically retry the expired stop.

Transport close and application cleanup then proceed independently. A supplied
`owner` must be the application's persistence owner, as with ExpressHost. The host
registers its HTTP drain with that owner's existing persistence/queue drains, and
accepted requests run inside the existing accepted-persistence and HTTP contexts.
Application drains can complete application-owned streams/connections while
Fastify is waiting for transport to close. Without a persistence owner, host request
drain precedes application cleanup, protecting borrowed modules in small standalone
compositions.

A root lifetime hook runs before prepared parsers/session hooks/actions. Route
handlers are wrapped through the existing `runHttpRequestHandler`, preserving
Fastify's handler `this` and return value. Finish/disconnect and action completion
are independent. Explicit callbacks/observations use `trackHttpRequestWork`;
existing detached follow-ups use `retainHttpRequestFollowup`. Hijacked replies use
the native response lifetime as well. Native session/store and scoped observation
bindings in later tasks must retain their callbacks through this seam; arbitrary
unreturned plugin work is not implicitly owned.

Application rollback can quiesce the registered HTTP resource before a startup
failure reaches the host. That resource closes admission by clearing activation;
it does not pretend that host stop already ran. The host still closes its listener
and signal handlers after application initialization/activation rollback.

Each caller attempt joins the previous application stop before explicitly retrying
failed cleanup. Deadlines do not cancel it or start duplicate consumer/pool closes.
A successful application stop is remembered even if transport failed. The existing
application/persistence protocol retains failed resources and borrowed Mongo pools;
this host does not close them. Only success of both transport and application
cleanup marks the host stopped/removes signals. Repeated successful stop is a no-op.

A failed Fastify-close promise stays failed on every later stop. Application cleanup
can still retry and finish. Single failures reject with the original error; combined
transport/application failures reject as `AggregateError`. Signals report through
the existing executable `onError` callback and never call `onStopped` for a transport
failure. The executable retains the existing responsibility for logging/exit code;
there is no new executable or process-exit policy here.

### P1 — Consumer and dependency cleanup

Application module factories can declare `requires: readonly string[]` naming the
modules they borrow through cleanup. The constructor snapshots and validates
these names, rejects missing/self/cyclic dependencies without running factories,
and maps module names to the existing persistence resource names. This metadata
does not reorder initialization or replace concrete constructor bindings.

Fastify's application registration enables dependency-aware persistence cleanup.
The existing resource registry remains the sole owner of drain/close/retry. A
consumer closes before the resources named by its `requires`. Successful consumers
are removed; failed consumers remain registered and retain their immediate and
transitive dependencies. Independent branches can still close. The cleanup graph
is retained across retries after successful resources are removed, so retry never
forgets a failed consumer's borrowers. Pools close only after every registered
consumer/dependency succeeds.

For resources/factories that omit dependency metadata, the existing
registration-order close contract is retained **conservatively**: all remaining
registered resources are treated as possible borrowed dependencies. A failure
therefore retains the entire downstream cleanup frontier. `requires: []` explicitly
marks an independent resource. Compositions whose initialization/registration order
differs from dependency cleanup order must declare the actual graph, including empty
dependency lists on its leaves. Invalid combined graphs fail cleanup without
releasing resources. The production Express composition does not enable this new
cleanup mode; its entrypoint and default lifecycle behavior are unchanged.

The graph regression registers the dependency before consumers to avoid relying on
registration order. `consumer → service → dependency` and `peer → dependency`, plus
an independent branch, exercise fan-in, transitivity and retry. The consumer's first
close fails. Peer/independent close once; service/dependency and Mongo stay open.
Retry closes the consumer successfully, then service, then dependency exactly once,
last among the modules; Mongo closes once afterward. A separate unannotated
consumer/dependency regression proves conservative frontier retention.

### P2 — Drain without the optional owner argument

`ApplicationRuntime.registerHttpHost` registers the host's request drain using the
application's own persistence owner before initialization. It returns that same
owner for accepted-request scopes; a supplied `options.owner` is validated against
it. Fastify uses this registration with or without the optional argument. A custom
application lacking the lifecycle registration fails composition with an actionable
message to implement `registerHttpHost` or use `ApplicationRuntime`; an inconsistent
owner also fails before acquisition.

Application producer drains and the registered request drain now start together
for every supported composition. This follows design section 10.2's independent
transport/work drains and FM-004's module/stream ownership: the stream module owns
the operation that finishes its response, while the HTTP owner waits for the actual
response lifetime. A no-owner-option regression keeps the client connected, sends a
hijacked response prefix, and lets module `drain()` send its suffix. Stop succeeds
and the client receives `prefixsuffix`. The same case runs with the explicit owner.

### Complete stop ordering audit

There is a partial order, not a serial wait for transport before application drain:

1. **Host admission closes synchronously**, readiness becomes false, concurrent
   stop calls join, and the application/integrations quiesce. Quiesce is a synchronous
   idempotent admission fence; it must not release dependencies or return async work.
2. **Join raw application initialization, HTTP preparation/readiness/listen and
   activation** under the caller's absolute deadline. Partial acquisitions retain
   their dependencies. Failure handlers are not joined cyclically.
3. **Begin the single tracked Fastify close**, and independently **begin application
   stop** (joining any earlier application stop first). Fastify's preClose/native
   listener close/onClose run on this transport branch. Close hooks own only
   Fastify resources and never await application stop or close borrowed modules.
4. **Application starts all producer/module drains and HTTP request drain together**.
   Queue/transfer/stream/socket owners can finish accepted work while HTTP waits.
   The HTTP drain includes returned actions, callbacks, session operations, explicit
   observations and retained follow-ups after response finish/disconnect. Acquire
   promises and accepted persistence work settle before resource closure.
5. **After all drains finish successfully**, close consumers in dependency order;
   close a dependency only when all registered borrowers have completed cleanup.
   Failed consumers retain their dependency frontier; independent branches may close.
6. **After all registered resources close**, close Prisma clients, then native and
   failed-acquisition Mongo clients through their existing owners.
7. **Only after both branches succeed**, mark the host stopped and remove owned
   signal handlers. A settled transport rejection is retained permanently, even
   while retryable application cleanup succeeds. Success is idempotent.

In the Fastify path every drain promise remains owned until settlement, even when
a peer drain rejects. Caller deadlines bound waiting; retry joins a still-running
cleanup instead of duplicating its live drains. A mixed rejected/held-drain
regression verifies this across two timed-out stops, then explicit successful retry.
Deadline checks before each later consumer/Prisma/Mongo close prevent late-settling
work from releasing another dependency after its caller's deadline. A close already
in flight remains owned and is joined; it is not canceled or duplicated.

### Queued plugin preparation belongs to startup

HTTP preparation and Fastify readiness now share one accepted persistence scope.
The internal host sets `pluginTimeout: 0`: Fastify/Avvio timing out a plugin cannot
cancel its underlying acquisition promise. Caller stop deadlines bound waiting
while retaining that work; the queued-plugin regression pins this configuration.

throws or stop interrupts it before the normal ready call. Stop also joins that
readiness barrier before starting its transport/application branches. Thus

### Final stop ordering and fault controls

1. Synchronously close admission, mark not-ready and quiesce application/integrations;
   concurrent stop calls share the same attempt.
2. Join raw acquisition/preparation/activation, **including every queued plugin's
   readiness**, within the absolute deadline. No resource closure is authorized
   before this barrier settles.
3. Begin the **one tracked Fastify close** and the retryable application stop
   concurrently. A previous application attempt is joined before an explicit retry.
4. Application starts producer/module/stream/socket and HTTP request drains together,
   with or without `options.owner`. This permits an application drain to complete a
   still-connected hijacked response; serial request-wait before app-drain would
   deadlock and is forbidden by design §10.2/FM-004 ownership.
5. Await every drain, acquisition and accepted persistence operation. Close modules
   through the one projected graph; failed consumers retain borrowed dependencies.
   Close other registered resources in their registry positions. A caller deadline
   prevents another close from starting; already-running work remains joined.
6. After resource success, close Prisma clients, then native/failed Mongo clients.
7. Only after **both** transport and application branches succeed, mark stopped and
   remove owned signals. Repeated successful stop is idempotent. A settled transport
   error stays rejected on all retries; application cleanup can still retry.

dependency and pool. Each row checks error visibility, synchronous admission,

### Final stop ordering / FM-004 audit

The round-2 ordering and failure/hang matrix remain authoritative:

1. Synchronously close admission/mark not-ready, set stop intent and quiesce all
   producers. Concurrent calls share one attempt.
2. Join raw application acquisition/preparation/activation **and queued plugin
   readiness**, within one inherited absolute deadline. No application resource
   close occurs while this work can still use it.
3. Start one permanent transport-close observation concurrently with Application
   cleanup. Application starts every resource drain, including HTTP request drain,
   together; an app-drained hijacked stream therefore works even without an explicit
   `owner` option. Transport finish is independent of retained work completion.
4. Await all drains, pending acquisitions and accepted persistence work. Only then
   close modules in the one prevalidated explicit dependency graph, projected onto
   acquired modules. Failed consumers retain their dependency frontier; unrelated
   branches may close. Close Prisma/Mongo pools only after consumers succeed.
5. Success requires both transport and application success. Remove owned signals
   and mark stopped only then. Deadlines retain raw attempts. Retry joins prior
   work before retrying failed application cleanup; permanent transport failure
   remains rejected/logged/nonzero according to the calling path. Successful
   repeated stop is idempotent.

The existing table-driven fault controls cover quiesce, acquisition/prepare,
activation, drain, retained request work, transport pre-close/on-close/native error,
module dependency cleanup and pool cleanup with failure/hang, retry, borrowed-state
and error-visibility assertions. Round-3 sealing does not weaken these controls.

## Round-4 public-view boundary

### Scope decision and implementation

The descriptor leak is verified: a proxy over the native request/reply object
guarded property reads but forwarded native own-property descriptors. A descriptor
for `reply.request` therefore exposed the raw request/server. Public route metadata
also needed the same boundary for nested configuration references.

The orchestrator's scope decision is now authoritative in
[design section 4.1](../design.md#41-sealed-http-composition-boundary): the seal
prevents **accidental misuse by trusted in-process first-party/extension code
through Fastify's documented public API**. Public-key descriptor access,
`Reflect.get`, destructuring and spread are included. Adversarial reflection,
Fastify-private Symbols/fields, constructor/prototype tricks and deliberate raw
integration-internal access are outside the contract. This is not a JavaScript
isolation sandbox. No extension receives a raw Fastify instance or a new plugin API.

`requestOwnership.ts` now uses one generic public-object proxy over a separate
target. Its `get`, `getOwnPropertyDescriptor`, `ownKeys`, `has` and
`getPrototypeOf` traps share the public-value boundary; descriptor values and
accessor results cannot return native Fastify objects. The separate target also
handles frozen metadata without violating Proxy descriptor invariants. View
prototypes are null, while native inherited public methods/getters remain
accessible by property access. Method/fluent/getter results cross the same boundary.
Public metadata records and arrays are traversed lazily, so nested
`request.routeOptions.config` references stay guarded. Identity is cached for
request/reply objects, metadata and preparation capabilities. Public view method
replacement/definition and prototype replacement are rejected.

Fastify continues to use its native objects internally. Fastify-private Symbol
properties are not forwarded by reads, descriptors, enumeration or `in`; no
reflection-hardening mechanism for their contents is added. Two internal protocol
exceptions remain: core's existing private request-lifetime Symbol is readable by
the shared source/built lifetime helpers, and metadata arrays retain the standard
`Symbol.iterator` through guarded indices. Hiding the core lifetime Symbol broke
explicit retained-work accounting during development; preserving this existing
seam avoids changing Express or introducing another lifetime registry. Native HTTP
streams, loggers and application-owned class instances retain their existing
borrowing boundaries. No additional Fastify registration API is allowlisted.

Runtime changes since round 3 are confined to `requestOwnership.ts` and the one
preparation call that registers each facade's stable identity. Tests change only
`FastifyClose.test.ts`; design and this evidence record document the scope decision.
The round-3 changes elsewhere remain, with their Express compatibility requalified.

## Round-5 capability-only views

### Findings, scope and implementation

All three findings have a shared cause: the round-4 generic proxy treated ordinary
request data as a capability and generically converted method arguments back to
native objects. An array's `forEach(callback, requestView)` consequently received
a raw request as its `thisArg`; its callback could reach raw Fastify. The same
proxy's unconditional deletion guard broke array `pop`, property deletion and
AJV's removal of additional properties. `writeEarlyHints` also had an unqualified
callback path. Those round-4 behaviors and its data-proxy description above are
superseded here.

The current split follows [design section 4.1](../design.md#41-sealed-http-composition-boundary):

- Only known Fastify capabilities cross a view boundary: preparation instances,
  request/reply, their transports, route metadata/configuration and logger/signal
  access. Public property, descriptor, Reflect, destructuring and spread access
  share the same cached capability mapping. Fastify-private Symbols stay omitted;
  the existing private core request-lifetime seam stays available.
- `body`, `query`, `params`, `headers`, cookies, validation data/errors, raw HTTP
  data fields and ordinary application values are native. Their array methods,
  `delete`, `Object.keys`, JSON and identity match native Fastify. Route options
  and nested configuration use cached frozen metadata snapshots, as do logger
  binding results. Only this explicit metadata is recursively copied; there is
  no generic request-data proxy.
- There is **no generic argument unwrapping**. Native data functions run as normal
  JavaScript; their `thisArg` remains the value supplied by the caller. Native
  Fastify methods use a named method catalog and their own trusted native receiver.
  Application-owned function fields are not classified as native methods. The
  narrow raw-object handoffs are the owned framework-stage return value, its
  request identification, and the Fastify callback-hook payload continuation.
- Callback early hints are deliberately **omitted**, as permitted by the review's
  adapt-or-omit direction. Access through `getDecorator` cannot bypass this rule.
  A clear `TypeError` occurs before the native method writes or calls the callback;
  no-callback hints retain Fastify's native 103 behavior. Unqualified raw callback,
  stream and AbortSignal surfaces fail with the same owned-hook/module-drain
  guidance. This avoids adding an unneeded second callback registry.
- `reply.send` rejects Node/Web streams and `Response` before starting a producer,
  including implicit sends by Fastify. Qualified later stream integrations must
  use their own documented module drains/hijack contract. Ordinary payloads and
  submitted promises retain their pinned Fastify behavior. `reply.then`, trailers,
  serializers, returned validation/serialization handles and all preparation
  stages keep the existing request work/lease accounting.

The scope remains **accidental misuse by trusted in-process code through the
public documented API**, not an adversarial JavaScript sandbox. Application-owned
handles and arbitrary user data are not recursively inspected for hidden
capabilities. Deliberate private-field/prototype/Symbol reflection is out of scope.
No registration API has been added; extension registration still uses only the
typed controller, route and named-hook stages. The registration allowlist/rejection table in round 3 remains current.
ExpressHost, the production composition and executable remain unchanged; this
round changes only the internal Fastify request adapter, its focused tests, design
section 4.1 and this evidence. Shared Application/persistence changes from earlier
rounds remain in the working tree and are requalified below against Express/Mongo.

## Round-6 outgoing payload handoffs

Historical qualification: the claim below that `pipe`/`getReader` and the Response

### Verified findings and single classification policy

Both findings are verified against the installed Fastify **5.12.8** implementation:
`lib/reply.js` uses `Object.prototype.toString.call(payload) === '[object Response]'`
in both `Reply.prototype.send` and `onSendEnd`. It does not use `instanceof Response`.
The already-installed **Undici 8.12.1** Response has that brand but is not an instance
of Node 26's global Response. A pinned native socket control asserts both facts
and successfully consumes its body. No dependency is added or upgraded.

`onSendHookRunner` in `lib/hooks.js` invokes `onSendEnd` directly with promise or
callback replacements; it does not go back through `reply.send`. Checking only
`reply.send` therefore missed those handoffs. `preSerializationHookRunner` shares
that runner. `lib/wrap-thenable.js` supplies implicit handler-result sends, including
fallback/error promises, while custom serializer results reach `onSendHook`
directly. These source paths, rather than constructor assumptions, determine the
new common boundary.

`requestOwnership.ts` now has **one** `payloadType` classifier and one policy
function `sendPayload`. The classifier mirrors the pinned source's detection
order: null/undefined; function-valued `pipe`; function-valued `getReader`;
object-branded Response; `payload.buffer instanceof ArrayBuffer`; string; other
values. Node stream duck typing is intentional. Response recognition is independent
of which implementation constructed it. Buffer, offset TypedArray/DataView and
buffer-bearing objects preserve native byte behavior. A bare ArrayBuffer is an
ordinary object under this version's test. Bare async iterables are also ordinary
objects: Fastify does not iterate them; only an object additionally exposing
`pipe`/`getReader` qualifies as a stream. Native controls pin these distinctions.

The policy rejects unqualified Node/Web streams and every branded Response before
native consumption, with the existing qualified-module/drain/hijack error. It
passes all other payloads through unchanged, leaving native serialization and
native invalid-payload errors intact. In particular, it does not normalize a
TypedArray on an onSend replacement: Fastify normalizes it only at `reply.send`,
and native onSend rejects a non-Buffer byte view. The socket differential retains
that distinction.

The same classifier runs at all outgoing handoffs below. The generic request-work
adapter has an explicit outgoing-result mode; it checks synchronous results and
resolved promises before handing them to Fastify. Callback hook replacements are
checked before calling the trusted continuation. A policy error is forwarded as
`done(error)` so asynchronous callback completion cannot throw an unowned policy
error. Returning undefined from a payload hook retains the old payload; that old
payload is rechecked after in-place mutation. Non-promise callback-hook return
values are ignored natively and do not constitute a handoff; their continuation
is checked instead. A dedicated regression pins this distinction.
