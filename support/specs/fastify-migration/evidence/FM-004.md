## Ownership and current lifecycle

The table names one accountable lifecycle owner for each resource. A parent
delegating to that owner is not another resource acquisition. It does **not**
claim that today's implementation invokes every close exactly once: Companion's
duplicate delegation and Socket.IO's borrowed-server close are called out below.
Source links refer to the inspected implementation, not the future design.

Three concrete constraints for FM-012/FM-021/FM-036:

- PortalHttp calls lifecycle methods on its resource array, while Companion also
  registers that **same instance** with persistence. Quiesce/drain/close may be
  invoked through both paths; its logical owner is CompanionUploads, not two
  independent providers. A future one-owner adapter must avoid concurrent duplicate
  close hooks and preserve partial-acquisition retry.
- Installed Socket.IO `dist/index.js` `Server.close` closes `httpServer` as well
  as namespaces/Engine.IO. ProgressSockets ignores its callback error. ExpressHost
  stores its own server-close promise. These are existing interactions, not proof
  that a Fastify transport close can be delegated to Socket.IO safely.
- `cleanupPersistence` drains every resource before closing any, and retains
  pools after a resource close failure. It still attempts other registered resource
  closes after a failure. PortalHttp itself closes its array in insertion order
  and stops on its first rejection. Do not describe this as reverse topological
  module cleanup or promise arbitrary borrowed **module** dependencies survive a
  consumer close failure. Fastify must establish the design's stronger boundary.

## Production security composition

[PortalHttp.prepare](../../../../packages/redbox-core/src/application/portal/http.ts)
is the production composition source. Characterizing only `mountXRoutes`, or a
fixture that stubs `prepareHttpMiddleware`, cannot establish absence of earlier
session/authentication/header work.

For ordinary requests the source order is:

1. Host exact GET health/readiness short-circuit, otherwise readiness admission.
   Begin request lifetime/accepted persistence scope before async work, then mount
   rootContext router. Protocol-level malformed requests may fail before Express.
2. Page headers, safe request chronicle, JSON then extended URL-encoded parsing,
   each 1 MB. Companion's configured case-insensitive segment prefix skips these
   ordinary parsers. Multipart/TUS content types are not consumed by them.
3. Owned session load, regeneration of authenticated incompatible-version session,
   Passport initialize and session deserialize. This includes OIDC HEAD denials,
   static assets, automatic OPTIONS and eventual fallbacks. Parser errors precede
   this stage and route policies. Static cookie suppression does not skip stores.
4. Extension integration preparation is startup work. At request time, extension
   `beforeRoutes` middleware and explicit routes run before core mounts; API1
   middleware may terminate. Core mounts follow the exact order in PortalHttp:
   CSRF/auth, root, literal record-type/metadata reads before pages, configuration,
   forms/query/record/identity/integration operations, uploads/downloads/TUS,
   optional Companion, progress, branding/dynamic/static assets, extension
   `afterRoutes`, branded fallback, safe error handler. This is not an onResponse
   observation chain. Socket.IO/provider upgrade paths are separate boundaries.
5. Within a matched core route, bind effective policies in order; then applicable
   CSRF/canonical-origin checks; then the action's own domain/input order below.
   Dynamic assets fill absent params before policies. Companion first chooses
   trusted session/default context and runs a scoped parser before policies.

Policy resolution preserves route-declared chain **then** most-specific normalized
action/controller/global configured mapping. Strip the exact `Controller` suffix
(the source replacement is case-sensitive), then lowercase the target;
default deny is `[false]`; keep effects in `['nocache', false]`. Public configured
`true` means an empty _configured_ contribution, not removal of route/mandatory
guards. Pages/branding/dynamic assets prepend mandatory chains and deduplicate;
Companion prepends pilot policies without deduplication. API1 extension `public`
is explicit; otherwise execute its named policies in order, with `csrf` mapped to
apiProtect only if named. Empty or unknown extension policies are not public.

The default API chain is noCache → brandingAndPortal →
isWebServiceAuthenticated → brandActor → checkAuth; schema routes substitute
checkRecordSchemaAuth and its problem response. Brand resolution rejects invalid
brand/portal before authentication. Session deserialization is still earlier.
Explicit invalid bearer outranks a valid cookie. BrowserActor resolves identity;
BrowserAuthenticated can redirect before brandActor; checkAuth independently
checks path roles and preserves anonymous redirects vs JSON/actor/schema denials.
Context/actor snapshots are frozen and roles filtered to brand; no claim of deep
immutability beyond the implementation is made.

`protect`: canonical Origin and Sec-Fetch-Site check **before** synchronizer token;
header token precedes body token. `apiProtect`: canonical-origin check **before**
independently verified bearer exemption, otherwise synchronizer protection. A token
never grants actor/tenant/object permission. Safe methods are skipped only where
the mount explicitly skips them: TUS invokes apiProtect even for HEAD/OPTIONS;
administration refresh GET also invokes it. Token acquisition itself checks origin,
generates token, **awaits session.save**, then replies.

## Per-route ordering and source reconciliation

[FM-004.ordering.json](FM-004.ordering.json) contains **335 route rows / 152 API
rows / 14 supplemental boundaries**, reusing every FM-002 identity exactly once.
No second route-name/hash rule is introduced. It includes method/path, original
controller/action/collection, shared prefix, pre-policy parameter resolution,
ordered effective policies, CSRF, HEAD behavior, schema metadata, reviewed action
order, response boundary, exact source unit and existing test references. Each
row also points to its production mount stage. The generator extracts the full
ordered `PortalHttp.prepare` registration list, including conditional Companion,
socket attachment, shared middleware, extension stages, static and fallback
registration. Callback definitions passed as collaborators are excluded from
that list; earlier mounts can terminate or fall through before a row is reached.

The generator first regenerates/checks FM-002 byte for byte. Unknown collections,
missing symbols or unannotated boundaries fail closed. It audits actual TypeScript
mount functions/classes and includes a deduplicated operation index with source
lines, condition/case branches and nested helper/callback scopes. **That index is
lexical AST preorder, not an execution trace or an interprocedural proof.** Helpers
do not execute at their definition positions; follow the row's action branch and
the referenced source. Action-order prose is a reviewed annotation, not a theorem
derived by evaluating guards. Full source fingerprints make changes require an
explicit audit/regeneration, including changes hidden behind the same schema shape.

  pagination still fails route Zod before lookup.

  an existing type exposes the field error. Browser missing type plus bad rows
  exposes the type error; malformed numeric API input still fails Zod first.

  return 404/403 before the later 400. Browser audit/integration-audit must retain
  their pre-actor scalar/pagination checks and post-object date/status checks;
  raw integration-audit API retains its earlier filter checks.

  an existing target exposes the 400 search-text error. User-list read/enrichment
