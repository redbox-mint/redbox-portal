## Implementation

- Public HTTP contracts and API2 declarations now expose named hooks/fallbacks.
  API2 inspection retains non-HTTP resolution/provider precedence; the same offline
  composition checks run in the extension resolver and controller host. No hook,
  observer, controller or resource factory executes during inspection.
- `http/fastify/hooks.ts` validates explicit route/application scopes, supported
  stages, bounded names, replacements and the same-stage dependency graph.
  Missing targets, cross-stage edges and cycles fail before host registration or
  acquisition. Stable eligible-node ordering uses dependency edges first, then
  existing low-to-high provider/declaration order; selected replacements take their
  winning provider/declaration position. Selected hooks/scopes/dependencies are
  copied/frozen.
- The native route binder normalizes captured params and executes its existing
  guard pipeline in Fastify route `preHandler`. The controller host runs prepared
  parsing/session/authentication, an optional explicit core context/authentication
  prelude, `afterAuthentication`, native access/CSRF, core domain-before-validation
  prelude, executable declared validation, `beforeAction`, then the action.
  The native validation wrapper accepts request-only metadata and reuses the
  existing shared validation/extraction primitives. The production shared validator
  is unchanged.
- Every early-submission boundary uses FM-016's shared `httpReplySubmitted`
  termination helper. No parallel error writer/denial mechanism is introduced.
  Pending async `onSend` cannot allow subsequent hooks/actions to execute.
- `onResponse`/`onError` bind the existing allowlisted owned Fastify hooks.
  Observers receive frozen detached data and sanitized errors, never live request,
  reply, session, headers/body/query, logger, server or transport capabilities.
  Their return values are ignored; each throw/rejection is isolated and logs only
  `HTTP_OBSERVATION_FAILED` through the existing redacting failure-isolated logger.
  Existing logger degradation/restart ownership from `logging.md` is retained.
- `http/fastify/fallbacks.ts` shares named replacement selection, validates access
  and literal prefixes, and selects the longest segment-boundary match. Equal
  effective prefixes need explicit same-name replacement. Fallback access/CSRF
  uses the exact native guard binder. Literal declared context becomes params for
  ordinary brand/portal policies; arbitrary unmatched paths never establish brand
  or actor identity. Unavailable required context fails closed. A denied specific
  fallback never falls through to a broader public fallback.
- Fallbacks use an encapsulated not-found handler under `/` on the same server.
  Core supplies complete reserved static/asset/integration roots even for
  missing files/methods. The actual registration registry reserves paths across all
  methods; existing actions/fallbacks calling `callNotFound` cannot re-enter portal
  dispatch. Probes, admission, HEAD/405, OPTIONS/unsupported methods, malformed or
  encoded/dot/empty-segment paths and reserved mounts remain outside fallback.
  No fallback registers a wildcard route or bypasses access checks.
- No preparation allowlist or public Fastify API was expanded. New work uses the
  existing qualified `register`/route `preHandler`/not-found/observation adapters.
  Returned hook/observer promises, explicitly tracked follow-ups and async logger
  work retain the existing accepted request/application owner through shutdown.

[Hook contract](../hooks.md) documents scope, ordering, context availability,
validation preludes, reserved mount ownership and migration. The design's
illustrative observation `FastifyRequest` argument is deliberately narrowed to
`HttpObservationRequest` to enforce its mandatory observation-only semantics.
The API2 fallback grammar deliberately fails closed for encoded/ambiguous unmatched
paths and excludes HEAD/OPTIONS; existing matched-route behavior is retained.
Static/asset implementation remains FM-031; core already supplies its complete
reserved mount roots. Existing production Express remains the default unchanged.

## P2 review corrections

The review identified two real gaps in the original implementation: fallback
protection consulted only declarative routes, and request-stage hooks bound only
those routes. Native authentication registered through `security.prepare` could
therefore miss application hooks and have method misses consumed by a public
fallback. An empty/incomplete mount list also failed to reserve unported FM-002
surfaces. The corrections below supersede those behaviors and the original gates.

- `registry.ts` is the single core ownership registry. The sealed preparation
  guard captures every actual normalized `onRoute` registration before ownership
  wrapping/freezing, including all methods, implicit/explicit HEAD, authentication
  providers and late nested plugins. It records descriptive native/declarative/
  automatic-OPTIONS identities, maintains a native matching index, and privately
  checks live Fastify `findRoute` across registered methods. Synthetic OPTIONS
  wildcard registration does not claim every path. Native wildcard asset mounts
  reserve the missing base root as well as descendants. No new API is allowlisted:
  private router results collapse immediately to booleans. `registeredRoutes()`
  exposes only frozen name/method/path/kind snapshots.
- `scripts/http-namespaces.cjs` derives the shipped `coreNamespaces.ts` catalog
  from all retained FM-002 route/integration paths and the actual core asset tree.
  Build checks drift; installed runtime reads compiled data, never repository or
  specification files. The 57-entry catalog includes 56 namespaces and one exact
  root path, global probes, static/asset/font/favicon roots, branded
  dynamic assets, API families and configurable Companion HTTP/upgrade roots.
  `coreFallbackReservedPrefixes()` is the complete core supplier. Defaults use it;
  explicit empty/incomplete lists fail offline with the omitted namespace, even
  when the omitted path overlaps another reservation. Extra roots are permitted.
  The same registry owns global probe reservations and captured route mounts.
- The first owned root `preHandler` runs `afterAuthentication` for every admitted
  route after parsing/session/authentication `preValidation`, before inherited
  policy/CSRF guards. Declarative normalization and optional context prelude run
  first. The registry appends owned `beforeAction` after every route's own
  preHandlers; declarative access/CSRF/domain-prelude/validation and native guards
  retain their order. Native action/domain logic is unchanged. Fallback selection
  is cached at the same first-stage boundary before inherited guards. All stages
  use the existing submitted-reply termination helper and request ownership.
  Observation hooks resolve native route identities through the same registry.
- `hookRegistry.test.ts` adds 21 cases beyond the original 53. They cover the
  actual native authentication `POST /user/info` regression, branded counterpart,
  late async native method misses, every catalog namespace root/missing descendant
  × all 35 Node methods × two root contexts (7,910 exchanges), every individually
  omitted reservation, configured Companion paths and native asset wildcard roots.
  They iterate every registered route to assert ordered application stages and
  guard boundaries, then all four stages on failures with safe native observation
  identity. Additional checks protect probe/admission behavior, private router
  capability, immutable snapshots, synthetic OPTIONS, slow-onSend termination and
  shutdown deadline/retry ownership for native hooks, plus synchronous/asynchronous
  native serializer fault containment after both stages. CONNECT without an owner is
  closed by Node; only its expected ECONNRESET is accepted, and fallback execution
  is still forbidden.
- Updated `hooks.md` documents universal binding and the fail-closed supplier.
  Express production, the shared production API validator, lockfiles, dependency
  versions and task checkboxes remain unchanged. `package.json` changes only the
  core build script to verify catalog drift. This is still FM-018, not asset
  implementation or later production/institution qualification.
