## Implementation and ownership proof

The private `http/integrations/companion` boundary owns provider loading, bounded
logging, the public app/socket/emitter integration, tracked transfer tokens and
upgraded sockets. The old Express files retain compatibility re-exports and the
retained Express mount delegates URL validation, canonical send-token generation
and audit ordering to the same transport-neutral actions as Fastify. Pure policy
configuration selection is extracted so native security does not execute Express
policy/session/authentication middleware.

Production `resolvePortalInstallation` selects its existing non-replaceable
`portal-raw-http` module when Companion is enabled, including deployments without
selected upload/progress routes. That module declares its borrowed domain edges
(including users for audit), constructs the adapter during application initialize,
and attaches it to the prepared Fastify server before listening. It alone owns
quiesce/drain/close for the production adapter; initialization explicitly borrows
that module's lifecycle instead of registering a second persistence resource.
Standalone adapter users retain their original direct resource registration.

The adapter replaces the old unlistened second HTTP Server with an **EventEmitter**
implementing the pinned provider socket API's server-event requirement. The
production probe asserts preparation before listen, exactly one listen call,
bridge is not an HTTP Server, and removal of owned upgrade/event listeners.
The production-cron child also asserts inert construction, one initialization,
permanent singleton rejection after stop and detached owned bridge listeners.
No listener, parser, signal handler, Mongo pool or stop owner is added elsewhere.

Native HTTP requests pass the existing host admission gate, scoped native body
parsers, native session/authentication, trusted brand/portal, configured policy
chain and CSRF before provider dispatch. URL-encoded parsing stays flat only in
the selected Companion prefix, matching Express extended:false; ordinary parser
behavior remains qualified by the affected security suites. All supported methods
are registered at the explicit configured root/mount. Hydrated configuration
selects metrics explicitly (default false). Both hosts forward the same optional
URL-import settings; normal provider defaults disable URL import/local URLs.

One private Express app supplies only the provider's real request/response
prototypes. It has no portal routing, authentication, session or policy middleware.
Private WeakMaps bind the core native request view to its owned request/reply;
there is no public raw unwrap or general middleware bridge. The raw request aliases
the same host request lifetime and borrows the native session object/save API.
The provider's first raw write waits for the actual native session commit, including
provider changes, then merges cookies and replays writes with normal callbacks and
pipe backpressure. Publishing and provider callback work remain owned after client
disconnect. Session-store failures go through the shared safe error writer before
provider bytes can be published.

Hijack bypasses Fastify serialization/onSend. The private publication barrier
supplies session writes/cookies; shared error/deny termination supplies safe faults;
native onResponse, request leases and module drain supply completion accounting.
Canonical HTTPS popup COOP is preserved through safe faults and documented provider
CORS is retained on public denials. Neither native authentication nor persistence
ownership is delegated to Express.

Upgrade admission reuses tracked Map tokens, bounded callback-token format,
canonical Origin, readiness and quiesce checks on the same server. Untracked,
prototype-looking, malformed, missing/foreign-Origin and late upgrades are denied
through the shared write/terminate helper. Companion and Socket.IO upgrades are
independent. Reconnect retains the tracked transfer rather than treating the first
socket disconnect as transfer completion. Provider terminal events/connect timeout
or the documented stop deadline release grants. Executing provider HTTP callbacks
and native session work remain owned until settlement, protecting borrowed pools
across deadline and explicit stop retry.

The implementation-level resource matrix and dependency justification are in
[companion.md](../companion.md). Required remaining Express dependencies are the
provider's Express app, request/response prototypes/routing/query helpers,
express-interceptor, cookie-parser and Grant Express adapter. Companion's package
graph also includes express-session/connect-redis, but this adapter starts neither;
native Mongo sessions remain the selected store. Existing unrelated first-party
Express composition remains for the production executable/oracle until cutover.
Redis and periodic ping services are refused because they expose no owned close
handles in this pinned provider.

## Production differential and negative controls

`companionMongo.test.ts` forks actual production portal bootstrap instances, first
with the immutable committed Express Companion class/mount, then with native
Fastify. It does not hand-assemble application modules or substitute portal action
switches. The oracle is compiled from `git show 5ba59694e:.../express/companion.ts`;
its revision and SHA-256 are asserted. Only the external disposable HTTP source/TUS
sink and deliberate store delay/failure probes are controlled.

The raw comparison checks status, representation/security/framing headers and
body; normalization removes only Date/connection/keep-alive and substitutes the
fixture's ephemeral upstream origin. It covers configured/case/trailing mount,
health/HEAD/OPTIONS, provider auth failure, canonical send-token, parser/input,
authentication/origin/CSRF precedence, flat forms and real URL metadata. Additional
cases prove actual provider logout session mutation persisted in Mongo before reply,
real URL-to-TUS bytes, destination allowlisting, brand roles before remote I/O,
tracked upgrade/reconnect, Socket.IO coexistence and bounded provider logs.

The shutdown case holds an active real transfer plus an external provider callback,
disconnects the callback client, and expires stop. The accepted WebSocket stays open
until the deadline, then closes; grants/sockets empty, the host remains unstopped
and borrowed pools remain open. Releasing the provider lets requests settle and an
explicit stop retry succeeds with exactly one underlying transport-close attempt.
Fixture close asserts stopped, zero pools and zero upgrade listeners **before**
process exit. Optional disabled mode has no native Companion routes/provider work;
configured policy denial reaches no remote provider work. Activation probes deny
both HTTP and upgrades before readiness.

The separate existing production-cron probe intentionally exits only after adapter
cleanup assertions. It proves the documented provider process-global limitation;
it is not used as transfer-drain proof.

## Limits and later work

After full stop Companion requires a **fresh process**. Its singleton emitter,
provider registry, daily cleanup cron and internal remote workers/clients lack a
complete public disposal API. The process guard is never reset. A deadline may
terminate owned sockets/grants without cancelling provider-internal remote I/O;
that work can still require eventual process termination. Transfer grants and
progress/session topology retain process affinity. No cross-replica continuity or
in-process restart is claimed.

The pinned Grant entry under a nonempty implicit root returns 404 in the retained
Express host as well: Grant matches originalUrl against server.path without
implicitPath. This test characterizes status and proves real provider logout
session mutations instead of claiming an external OAuth exchange. Grant fallthrough
reaches the outer Express page fallback (empty 404); the native pilot's outer
fallback is JSON 404. That page body/header conversion remains later work and is
explicitly outside the provider raw differential. Institutional OAuth, remaining
provider routes, portal TUS callback conversion and the full FM-035/FM-036 matrix
are unqualified here. No FM-022 or later implementation was started.
