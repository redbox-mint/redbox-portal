## Verified findings

### R3-S1 — P1: Observable/Effect wrappers let timed-out hooks escape the owner and retry concurrently

**Primary location:** `packages/redbox-core/src/action-execution/legacy-result.ts:69–73`, `adaptLegacyHookResult`. Supporting locations: `action-execution/executor.ts:178–191` (timeout), `:207–216` (retry gate), `records/Records.ts:3617–3631` (tracks only a directly returned thenable), `action-execution/executor.ts:345–363` (supervisor removes the completed fiber).

**Trigger:** An ordinary supported configured post hook returns `defer(() => opaquePromise)` or `Effect.tryPromise(() => opaquePromise)`, with `timeoutMs: 10` and idempotent timeout retry enabled. The Promise performs asynchronous I/O or persistence after awaiting a gate. Both wrappers are unconditionally classified as cooperatively cancellable. Interrupting the fiber only unsubscribes/stops awaiting the Promise; it does not stop the Promise body. Unlike the directly returned Promise path fixed in round 1, these actual lifetimes are never registered. The executor retries them concurrently, and drain reports clean stop with the original work still pending. With no retry configured, one unowned lifetime still remains.

**Verified evidence:** `probe-wrapped-promise.cjs` / `.log`, using actual Records, ApplicationRuntime, persistence admission and adapters (no Docker/database). For **each** return type: `attempts: 2`, `stoppedBeforeCompletion: true`, then `completedAfterStop: 2`; application status was `stopped`, `cleanupPending: false`, `operations: 0`. The late write was refused as `Persistence is unavailable or draining.` This demonstrates actual asynchronous code continuing after a successful stop, not merely a rejected new admission.

**Exact requirement:** design.md:322–323: “Cancel safe work where supported; preserve ownership for non-cancellable effects until they settle or stop fails observably.” design.md:406: “Report clean stop only when every required owner has completed cleanup.” design.md:417–419: “On timeout or cleanup failure, retain resource ownership for retry, surface the incomplete stop and block the upgrade procedure. Do not close pools under work that still needs them.”

**Regression:** Through the production hook composition, cover both Promise-backed Observable and Effect results across action timeout and application stop deadline/retry. Assert no second invocation overlaps non-cancellable work; stop fails/retains ownership while gated; releasing the gate lets the write and audit finish; retry closes clients exactly once. A cancellation flag based solely on the returned container type is insufficient evidence of cancellation.

### R3-S2 — P1: Agenda's own drain deadline revokes completion permission from a still-owned job

**Primary location:** `packages/redbox-core/src/queues/AgendaQueue.ts:122–124`, `drainWorkers`; independently `:194–195`, `withDrainDeadline`. Admission uses the revoked flag at `:83–90` and `:410–412`.

**Trigger:** An accepted job remains in flight longer than the queue's configured `drainTimeoutMs`, then performs a required completion enqueue (`queue.now`, e.g. audit submission) before a cleanup retry. Both timeout callbacks permanently set `completionAdmission = false` even though the handler, its worker context and its accepted persistence scope remain alive. Retry retains the job but can no longer complete its required queue writes. Preserving the original deadline does not justify revoking the live owner's completion capability after reporting the stop failure.

**Verified evidence:** `probe-queue.cjs` / `.log` runs the real accepted-job wrapper, AgendaQueue quiesce/drain and persistence scope with a 15ms queue deadline and a controlled Agenda port. First drain fails while `operations: 1`; releasing the still-running job causes `AgendaQueue is draining; restart before queuing work.`, and zero completion/audit jobs are queued. Retry then finishes. Existing `QueueMongo.test.ts:355+` expires the *host* deadline while using a longer queue deadline and therefore does not cover this failure.

**Exact requirement:** design.md:411–412: “Completion writes needed by draining jobs remain permitted within their admitted scope, while unrelated new operations are rejected.” tasks.md:390–391: “new work is denied while admitted completion proceeds; timeouts/failures retain ownership for retry”.

**Regression:** Expire the **queue's own** deadline with a gated accepted job. Verify unrelated submissions remain denied, the first drain fails retaining clients/handler ownership, the job can still enqueue its scoped audit/backend completion, and a subsequent stop succeeds. Include a late unscoped descendant negative control.

### R3-S3 — P1: Tracked record post hooks from queue/schedule work lose the admitted persistence lifetime

**Primary location:** `packages/redbox-core/src/records/Records.ts:627–647`, `retainHookFollowup` / `hookExecutionDependencies`; production binding at `application/portal/data.ts:229`.

**Trigger:** A built-in queue handler or schedule saves/updates a record and launches a configured asynchronous `post` hook. The handler returns before the post hook finishes, as the post API permits. Records retains the Promise/fiber for drain, but its production binding retains only an HTTP lifetime. Outside HTTP, `middleware/requestLifetime.ts:173–177` simply returns the Promise, which this void caller ignores. The job's `runAcceptedPersistenceWork` settles and marks its scope inactive (`persistence/runtime.ts:299–301`). During stop the retained hook therefore cannot finish its next repository write, even before Agenda's deadline expires. This is a platform-owned post hook, not an arbitrary unregistered detached descendant.

**Verified evidence:** `probe-records-worker.cjs` / `.log` runs actual `triggerPostSaveTriggers`, the production-equivalent binding and accepted persistence runtime. Stop with a 10ms outer deadline correctly retains cleanup; when the gated hook resumes its one write is denied: `attempted: 1`, `committed: 0`, `Persistence is unavailable or draining.` Retry reports success after the required hook failed.

**Exact requirement:** design.md:401–402: “Quiesce producers and drain accepted requests, callbacks, session writes, byte streams, jobs and scoped completion/audit/backend writes.” design.md:411–412: “Completion writes needed by draining jobs remain permitted within their admitted scope, while unrelated new operations are rejected.” extensions-v6.md:108–109: “Upload/socket/native owners use this resource contract and keep real work, including late completion writes, owned.”

**Regression:** Use an actual accepted Agenda/schedule callback that saves a record with a delayed post hook and returns. Stop before the hook's repository write, fail the deadline, then release it. Assert the hook's write and audit succeed in an explicitly owned live scope, unrelated callers stay denied, and retry drains. Cover Promise, Observable and Effect return types and HTTP as a control.

### R3-S4 — P1: Production email success callbacks are drained without completion admission

**Primary location:** `packages/redbox-core/src/application/portal/providers.ts:67–69`, email `retainFollowup` binding; callback dispatch at `integrations/Email.ts:354–380`. The global pending Set at `application/portal/application.ts:111–118,374–383` owns only settlement, not the callback's accepted persistence scope.

**Trigger:** A supported `onNotifySuccess` callback is asynchronous and performs persistence after the sending request/job has returned. Unlike Records' HTTP binding, the email provider only calls the global followup tracker. A stop retains this callback yet denies its next write because the original scope already settled. The built-in `Records.updateNotificationLog` with `saveRecord: true` performs a real mutation (`records/Records.ts`, `updateNotificationLog`); a delayed database/provider callback before that mutation is sufficient. This applies to HTTP as well as workers.

**Verified evidence:** `probe-email.cjs` / `.log` uses the **actual `portalProviderPlan.email` binding**, actual Email callback dispatch, ApplicationRuntime and persistence runtime; only template/send ports return a controlled successful response. Stop first fails while callback ownership remains; after release the callback write is refused (`committed: 0`, `Persistence is unavailable or draining.`); retry reports clean stop.

**Exact requirement:** design.md:401–402: “Quiesce producers and drain accepted requests, callbacks, session writes, byte streams, jobs and scoped completion/audit/backend writes.” design.md:417–419: “On timeout or cleanup failure, retain resource ownership for retry, surface the incomplete stop and block the upgrade procedure. Do not close pools under work that still needs them.”

**Regression:** Send an email through production composition with a gated `onNotifySuccess` callback that later performs `updateNotificationLog(saveRecord: true)`. Finish the HTTP response/job, start stop, assert a bounded deadline failure, release the callback and require the actual notification write/audit to succeed before clean retry. Include an unowned stale-scope negative control.

### R3-S5 — P1: Timed-out configured vocabulary imports escape awaited startup and clean stop

**Primary locations:** `packages/redbox-core/src/vocabulary/FigshareVocabulary.ts:2277–2285`, `processBootstrapImport`; `packages/redbox-core/src/vocabulary/Vocabulary.ts:1240–1262`, `importRvaBootstrapVocabulary`. Production stages are registered at `application/portal/application.ts:432` and `application/portal/reference.ts:499`. FigshareVocabulary uses `noDomainResources` at `application/portal/providers.ts:241`; neither vocabulary owner retains the original import Promise for drain.

**Trigger:** A configured Figshare import exceeds 120 seconds; or an RVA import remains pending past its 30-second primary timeout and 30-second reconciliation window. `promiseWithTimeout` only stops awaiting. Figshare catches that timeout and returns from bootstrap while `runBootstrapImport` continues. RVA likewise throws the settlement timeout and its bootstrap caller catches it. RVA also returns early if the vocabulary row appears before the original import has fully settled. Startup can finish, activate normal work and successfully stop while those imports are still awaiting network/disk work; their later repository writes are rejected or their external effects continue after clean stop. No retry of the import itself is necessary to trigger this.

**Verified evidence:** `probe-figshare-bootstrap.cjs` / `.log` runs actual `bootstrapData` and `runBootstrapImport` continuation through ApplicationRuntime's named `postBootstrap` stage. Only filesystem input and the delayed preview port are controlled. The real next `getRun` is attempted after clean stop and receives `Persistence is unavailable or draining.` `probe-rva-bootstrap.cjs` / `.log` runs actual Vocabulary bootstrap and its timeout/reconciliation code through a named `coreBootstrap` stage, with a delayed RVA import port. Both show `stoppedBeforeImportContinued: true`, `continuedAfterStop: true`, zero retained operations and clean stopped status. The probes accelerate **only** the specified 120000/30000ms import timers to 15ms (and RVA backoff to 1ms); they do not edit source. The existing still-pending RVA timeout test asserts rejection/one invocation but never asserts underlying ownership through application stop.

**Exact requirement:** design.md:364–366: “Required core-data writes, schema setup and configured vocabulary imports may perform persistence or network work, but they must be named, awaited stages with failure behavior.” design.md:322–323: “Cancel safe work where supported; preserve ownership for non-cancellable effects until they settle or stop fails observably.” design.md:417–419: “On timeout or cleanup failure, retain resource ownership for retry, surface the incomplete stop and block the upgrade procedure. Do not close pools under work that still needs them.”

**Regression:** Gate an actual Figshare/RVA import beyond each import/reconciliation timeout. Require readiness to remain correctly classified and the original import to remain drain-owned; stopping must fail with retained resources until it settles or is genuinely cancelled/joined. Release it, verify its final repository writes and cleanup, then retry stop. Include the RVA early-row reconciliation path, not merely absence of overlapping retry attempts.

### R3-S6 — P1: OCFL writable abort does not join its underlying disk upload

**Primary location:** `packages/redbox-core/src/services/oni-v2/flydriveOcflStore.ts:238–240`, returned Writable `destroy` callback. Upload starts at `:225`; only successful `final` joins it at `:230–235`. The catch at `:242` observes rejection but does not retain the upload beyond stream destruction.

**Trigger:** An OCFL write is aborted or its source errors while the configured Flydrive disk's `putStream` is still completing/cancelling network I/O. `destroy` destroys the PassThrough and immediately calls `callback(error)`, so the Writable's finished/pipeline/Web Writable abort completes and the enclosing Oni accepted operation settles. `Oni.pending` therefore becomes empty even if disk upload/abort cleanup has not settled. The disk may be a raw FS/S3 driver (`ioDisk` resolves `.driver` at `:146–150`); StorageManager supplies no independent drain owner for these raw drivers. The supported OCFL transaction API calls `_store.createWritable` (`@ocfl/ocfl/lib/transaction.js:286`), which converts this exact Writable via `Writable.toWeb` at `:251`.

**Verified evidence:** `probe-ocfl-abort.cjs` / `.log` uses the actual store class, actual Oni `retain`/drain and ApplicationRuntime. A controlled disk port keeps its upload/abort promise pending after the caller destroys the stream. The caller finishes, application reports clean stop with no operations/resources, and only afterward does the upload settle (`uploadStillPendingAtCleanStop: true`, `uploadSettledAfterStop: true`). This verifies the missing join boundary; it does not claim a live S3 experiment.

**Exact requirement:** design.md:409–411: “An aborted transport may cancel safe, cancellable work; already-accepted writes and their cleanup retain ownership until settled.” design.md:406: “Report clean stop only when every required owner has completed cleanup.”

**Regression:** Use a disk whose `putStream` observes source destruction but waits on a gate before finishing abort cleanup. Abort the OCFL writable (both Node and Web stream forms) and stop the application. Require incomplete stop/retained ownership until upload cleanup settles, then successful retry; include upload rejection and successful normal finalization to guard against hangs/unhandled rejection.

### Ownership conclusions by subsystem

- **Records/action executor/R2:** Direct Promise hooks, the audit grace enqueue and the returned fiber are explicitly retained. A returned fiber settling after interruption does not prove the opaque Promise inside an Observable/Effect settled (S1). An owner waiting for a Promise does not keep a worker's expired admission scope alive (S3). These were followed through Records' hooks, coordinator, adapter, retry predicate, supervisor and the production composition ports.
- **Agenda/schedules:** Job handlers, claim/release sequences, backend calls, start/drain operations and scheduled callbacks have retained sets/promises. node-schedule Jobs are cancelled at quiesce and running callbacks are joined. Agenda's original deadline race preserves cleanup ownership, but its own timeout separately removes permission from still-owned completion work (S2). Retry therefore needs both lifetime retention and live scoped completion permission.
- **Email/audits/security/Solr/workspaces:** Production queue/audit/security/Solr operations are retained or synchronously handed to Agenda; workspace loops collect and join emitted update Promises. Email's post-send callback settles under a global pending tracker without a fresh accepted scope (S4). Merely returning a Promise to an event/Observable callback is not assumed to register its lifetime.
- **PDF/RAID/Figshare worker:** PDF keeps generation/retry fibers and retained failed cleanups, with scoped/masked acquisition and joined finalizers; supersession does not remove an unsettled old fiber. RAID's main fiber is joined, its real HTTP adapter receives the abort signal and the abort listener is removed in finally. Figshare's repeating heartbeat stores one heartbeatTask, clears its interval and awaits that task in finally before releasing the lease. No further concrete escape was verified in these paths.
- **Bootstrap:** The named outer stage is awaited but the real import is abandoned after a timeout/reconciliation return (S5). Readiness and a drain registry must refer to actual import settlement, including the RVA early-row path.
- **Native storage/uploads:** Lazy GridFS cursor work, initialisation, read/write streams, multipart and tus accepted writes are retained through their owners and cleanup. OCFL's normal finalization joins the upload, while its abort path releases the enclosing operation too early (S6). A library Promise that has only a rejection observer is still pending native work.
- **Companion:** Adapter-owned transports, transfer/request promises, timers, sockets and attached listeners were followed through stop. The specification's existing pinned-Companion limitation leaves some internal provider I/O/cleanup cron process-owned after its deadline; it is recorded as a documented limit in the inventory, not reported as a new defect.
- **Browser:** Angular/DOM/Uppy/map/form subscriptions are marked with their actual view/component/form-object/document owner and disposer where one exists. Finite browser HTTP Promises and one-shot UI callbacks are explicitly identified when they have no join/cancellation on component destruction. A server's accepted request is separately owned after the browser dispatches it. The inventory does not claim every legacy UI subscription has an explicit unsubscribe.
- **Unselected exported utilities:** CoreService.exec, the Users trigger wrapper, nested Email.sendTemplate subscriptions and CacheService.set lack their own asynchronous lifetime registration; CacheService bootstrap also constructs a library timer without a disposer. No selected production invocation was found. They remain fully enumerated, with their limitation visible, but are not promoted into speculative normal-route findings.
