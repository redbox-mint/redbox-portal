ReDBox admin interface audit

27 screens reviewed as the local admin: every /admin page route in routes.config.ts, all 11 registered app-config editors (3 of which aren’t linked from the sidebar), and the Parties lookup that the sidebar links to. Findings are grouped into cross-cutting issues, then listed screen by screen.

Fixed so far (round 1, uncommitted on develop)
  • Rebuilt the running site from current source. Export now shows the async export screen, Dashboard configuration loads its metadata, and API docs renders.
  • Webpack builds again: svgo 4.1.0 and dompurify 3.4.17 are now pinned exactly as root dev dependencies.
  • RAiD publishing and Integration notification show their fields: an empty or partial field order now falls back to schema order (AppConfigService and the app-config form, with tests).
  • Added English text for menu-onipublishingconfiguration and party-title-label.
  • Still open: Oni publishing nested sections render no fields. That’s a schema limitation, left for the config-form redesign.

Cross-cutting issues

Mostly fixed

Broken or empty screens

At first audit: Dashboard configuration failed to load its metadata; RAiD publishing and Integration notification had no fields; API docs stayed on its loading animation; Parties showed “Update party-title-label”. All of these are fixed in round 1. Still open: Oni publishing’s six sections have no fields. API docs still opens outside the admin shell with no way back, which is a layout problem, not a bug.

High

Navigation gaps

DOI publishing, RAiD publishing, Integration notification and API docs have no sidebar link. The sidebar has no active state, so you can’t tell which page you’re on. (The raw menu-onipublishingconfiguration label is fixed.) The “Navigation” group also holds Figshare and Oni publishing. Parties opens /dashboard/party and loses the admin shell.

Medium

No consistent page header

Six title styles are in use: a centred H1 (Deleted records, Report view); a red card title only (Users, Roles, Harvest runs); an H1 repeated as an H2 (System messages, Web analytics, Authorized domains, Oni); no title at all (Export, Named queries, Vocabularies); a small left-aligned H3 (Figshare vocabularies); and a plain H1 (Reports, Menu). There are no breadcrumbs or descriptions, and every page has an empty gap of about 80px above its content.

Medium

Too many button styles

Three blues are in use: Bootstrap primary #0d6efd, legacy #428bca for the uppercase “SUBMIT”, and cyan “info” for secondary actions (Manage named queries, Import from RVA, Add language, Generate preview, Edit display name). Green is used for Publish. Primary actions sit top-left, top-right, inline or bottom-left depending on the page. Solid red Delete buttons appear on every table row.

Medium

Tables, filters and empty states vary

Four table styles are in use: bordered, borderless, sortable, and a tiny uppercase header around 8px that’s hard to read. Filters come in four layouts: a centred label-and-field panel, an inline row, stacked radios and segmented buttons. Some empty states are a bare header row (Roles, Deleted records, Report view); others use a dashed box. Counts appear as floating grey pills in some places and as stat tiles in others.

Medium

Long config forms are unstructured

App-config pages are raw schema output: Figshare publishing is about 8,900px tall and DOI publishing about 8,100px. There’s no section navigation, no indication of unsaved changes, no way to test a connection, and a single uppercase SUBMIT at the very bottom. Translations renders all 2,022 rows in one table, making the page about 103,000px tall.

Low

Width, locale and copy

Content widths vary: Roles is a centred 625px card, Users is 955px, Deleted records and the forms are full-bleed. Date fields mix text dd/mm/yyyy (Export, Report) with native mm/dd/yyyy pickers (Harvest runs). Sidebar labels mix title case and sentence case (“Menu Configuration” vs “Figshare publishing configuration”).

Keep

What already works

The red panel header (Reports, Vocabularies, Named queries, Translations) is on-brand, and the mocks reuse it. The stat tiles on Reports, the live previews on Menu, Home panels and Admin sidebar, the Users toolbar, and the Branding token groups are good foundations to extend rather than replace.

Design principles for the mocks

  1. One page header: breadcrumb, H1, one-line description and right-aligned actions on every screen.
  2. One container: the existing red panel header for primary lists; white section cards for forms.
  3. One button scale: blue primary (theme --rb-primary), outline secondary, outline-red destructive. Solid red only inside confirm dialogs. No cyan, no uppercase.
  4. One table, one filter bar, one empty state, all from the pattern kit.
  5. Long config = section rail + sticky save bar with enable switch, connection test and unsaved-change status.
  6. Regrouped sidebar with an active state, status tags and every registered screen reachable.
  7. All colours come from the existing theme tokens in theme.css, so brand overrides keep working.
